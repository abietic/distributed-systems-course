### 1. 写偏斜是不是「查询写错了」？

**你说得对的部分**：在 MySQL RR 下，这个例子的正确写法就是把决策前提做成当前读并加锁。`SELECT count(*) … FOR UPDATE` 会让 Bob 的事务在 SELECT 这一步排队。等 Alice 提交后，Bob 读到 1，自己放弃。课件 §4.6 表格的最后一行也是这个结论。所以从工程上讲，RR 下的写偏斜可以说成「SQL 没有按这个隔离级别的要求来写」。

但「写偏斜」这个词要说的是另一件事：**它描述的是隔离级别的契约，不是某段 SQL 的对错。**

- 可串行化的承诺是：每个事务单独跑是对的，并发跑也一定对，写代码的人不需要知道别人会同时做什么。你说的「完全线性执行就不会有问题」，就是它的定义。
- 写偏斜，就是 RR/SI 允许、但任何串行顺序都产生不了的那种结果。它是 SI 和可串行化之间差出来的那一块。
- 所以「查询方式合不合理」，取决于你站在哪个隔离级别上。同一段 SQL 在 SERIALIZABLE 下完全正确，在 RR 下就有 bug。RR 把「哪些读是决策前提、需要手工变成锁」这个判断交给了你。
- 你的做法，本质上就是给这个事务手工实现 2PL。MySQL 的 SERIALIZABLE 做的正是这件事：在关掉 autocommit 时，它把所有普通 SELECT 自动改成 `SELECT … FOR SHARE`（官方文档原话）。

手工加锁和自动加锁有三点区别，值得记住：

1. **你的 FOR UPDATE 反而比自动的更好。** SERIALIZABLE 加的是共享锁，两个事务都拿得到。接着两边都要升级成写锁，于是死锁，数据库回滚其中一个，靠重试收场。FOR UPDATE 在读的时候就是排他锁，第二个事务直接排队，不会死锁。
2. **难的是「找全」。** 决策前提可能来自另一张表、另一条查询、应用缓存，甚至上一个 HTTP 请求。每个事务单独评审时都是对的，这正是写偏斜难查的原因。可串行化的价值，就在于不需要人去找。
3. **这一招不是处处都灵：**
   - PostgreSQL 不允许 `FOR UPDATE` 和聚合一起用。文档原话是：锁定子句不能用在返回行无法对应到表中单行的场合，聚合就是例子。所以只能先锁住行、在应用里数，或者锁一个代理行。
   - 如果前提是「不存在」，比如「这个会议室的这个时段没人订」，那就是幻读型写偏斜：
     - MySQL RR 下，有索引时间隙锁能挡住。两边都拿到间隙锁、再各自插入时会死锁，回滚一个，最终结果是对的。
     - 到了 RC（没有间隙锁）或者 PostgreSQL，结果为空的 FOR UPDATE 什么也锁不住，写偏斜照样发生。这时只能物化冲突，或者上 SERIALIZABLE。

**结论**：写偏斜不是数据库的 bug，也不能简单归为 SQL 写错了。它是 RR/SI 这份契约里的一条免责条款：在这个级别下，要写对 SQL，就得自己显式锁住决策前提。不想操心这件事，就得付可串行化的价钱。

课件里「所有防线都失效」这句话，指的是不改 SQL 时数据库自带的防线。这一点我原来写得不够清楚。

### 2. 沙盒 D2 是不是推翻了「状态机永远不需要 undo」？

我理解你的意思是：D2 里 n2、n3 上那 5 条写已经提交、已经 apply，后来却被 n1 覆盖了，所以「不需要 undo」被推翻了；而「applied 永远在 committed 以内」推不出「不需要 undo」。

**你的推理是对的。** 「不需要 undo」要两个前提同时成立：

- (a) applied ⊆ committed：状态机只执行已提交的条目。
- (b) committed 永不回滚：这就是 State Machine Safety。它依赖 Leader 完整性，而 Leader 完整性又依赖 currentTerm、votedFor、log 这三样持久化状态不丢。

课件 §3.24 只写出了 (a)，(b) 被当成了理所当然。可真正不平凡的恰恰是 (b)。

D2 里清空 data dir、再用原来的身份重启，等于让节点失忆，(b) 的前提就被打破了。在这个前提之外，Raft 的所有保证都不成立，「不需要 undo」也跟着失效。

还有更诡异的一点：这个集群半年前第一次选出的 Leader，很可能也是任期 2。失忆之后，历史上就出现了两个任期 2 的 Leader。日志匹配性质依赖的「同 index 同 term ⇒ 内容相同」，根基就没了。

**那 etcd 里实际会发生什么？** 这里要修正课件的描述：结果（5 条确认过的写没了）是对的，但机制写错了。

- **已提交的条目不会被 AppendEntries 截断。** etcd 的 `maybeAppend` 如果发现冲突落在已提交范围内，会直接 panic（`entry %d conflict with committed entry`）。这是它有意的选择：宁可崩溃，也不静默 undo。
- **5 条写实际是被快照整个换掉的。** 运行了半年的 n1 早就压缩过日志：默认每 10 万条打一次快照，之后只保留 5000 条。n1 当选后向 n2 回退探测，探到 index 9 附近时发现这一段已被压缩，就改发快照。n2 收到的快照 index 远大于自己的 commit，于是整体替换状态机。
  - 正常情况下，快照一定是 follower 已 apply 状态的延伸，替换等于快进。只有在失忆这种前提被破坏的情况下，替换才变成了 undo。
- **谁当选，取决于谁先超时。** 课件把这一步简化成了「n1 当选」。实际上，n1 回来、把现任 Leader 逼下台之后，如果是 n2 或 n3 先超时，它们俩的票就已经够过半，那丢掉的就是 n1 这半年的数据。两份历史都声称自己已提交，Raft 没有办法合并，只能丢掉一份。

所以运维上的规则是：**丢了数据的节点，永远不能用原来的身份回来。** etcd 的 `snapshot restore` 会故意改写成员 ID 和集群 ID，文档写明，目的就是「防止新成员误加入已存在的集群」。

### 3. 意外宕机、网络隔离怎么办？remove/add 会不会改变集群规模和集群 ID？

「先 remove 再 add」只针对「数据目录丢了」这一种情况，不是用来处理重启的。按情况分：

| 情况 | 数据目录 | 该怎么做 | 成员配置变吗 |
|---|---|---|---|
| 进程崩溃、断电、机器重启 | 完好 | 原样重启。靠三样持久化状态和日志/快照追赶，全部自动完成；`--initial-*` 参数会被忽略 | 不变 |
| 网络隔离 | 完好 | 什么都不用做。恢复后它会追日志或接收快照；PreVote/CheckQuorum 防止它带着高任期回来捣乱 | 不变 |
| 磁盘坏了、data dir 丢了 | 丢失 | 先 `member remove` 旧成员，再 `member add` 新成员，用空目录加 `state=existing` 启动 | 变：旧 ID 作废，换成新 ID |
| 过半成员都丢了数据（D1） | — | remove/add 本身也需要过半才能提交，这条路走不通。只能在幸存者上 `--force-new-cluster`，或者用快照恢复 | 变 |

**remove 和 add 确实会改变集群总数，所以顺序很重要。** 假设 3 个成员，其中 n3 已经坏了：

- **先 remove**：剩下 {n1, n2}，过半是 2，两台都活着，没问题。再 add n4：变成 {n1, n2, n4}，过半是 2。n4 还没启动也不要紧，n1、n2 已经够了。
- **先 add**：变成 {n1, n2, n3, n4}，过半变成 3，可活着的只有 n1、n2，立刻失去过半。万一 n4 起不来，连把它 remove 掉的变更都提交不了。

etcd FAQ 专门写了要「先 remove 再 add」。默认开启的 `strict-reconfig-check` 也会直接拒绝这种会导致失去过半的变更。

**长期连不上的 follower 会被自动踢掉吗？** Raft 和 etcd 都不会。一个下线了三个月的成员仍然算在 N 里，悄悄吃掉你的容错能力。

原因回到 Part 0：系统分不清「慢」和「死」，而自动缩小集群会悄悄降低数据的持久性。踢不踢，是上层控制面的决策：

- TiDB 的 PD：一个 store 超过 `max-store-down-time`（默认 30 分钟）没有心跳，就在别的节点上补副本。
- CockroachDB：超过 `server.time_until_store_dead`（默认 5 分钟），就重新补副本。
- 它们补副本的顺序都是：先以 learner 身份加入 → 追平 → 提升为投票成员 → 移除坏掉的副本。learner 不计入过半，所以不会踩到上面「先 add 导致失去过半」的坑。

**会不会影响集群 ID？** 不会。集群 ID 在集群创建时由初始成员 ID 算出，之后固定不变。

- 成员 ID = sha1(排序后的 peer URL + 集群名 + 时间)。
- 初始成员不带时间，集群名就是 token，所以算出来的结果是确定的。这正是 D1/D2 的陷阱：只要 token 相同、列表相同，就能冒充旧成员。
- `member add` 会把当前时间也算进去，所以即使 URL 一样，得到的也是全新的 ID。
- 被 remove 的 ID 会被永久记住。它如果回来，会自己停掉，报错是「the member has been permanently removed from the cluster」。
- 真正会产生新集群 ID 的，只有新建集群和 `snapshot restore` 两种情况。

### 4. AppendEntries 里的「如果」和「截断」

你说的是 Leader 这一侧，这部分是对的：成功后 match = prev + len(entries)，而且 match 只增不减（etcd 的 `MaybeUpdate` 只接受更大的值）。问题出在 **follower 那一侧**。

「截断」指的是 follower 删掉自己日志从某个位置开始的尾巴，即 `log = log[:i]`。

Figure 2 接收方规则 3 的原文是：**如果**已有条目和新条目冲突（同 index、不同 term），才删除这一条及之后的全部。那个「如果」要说的就是：只有冲突时才截断。

常见的错误实现是：不管有没有冲突，一律「截到 prevLogIndex，再追加」。在网络会乱序的情况下，这样做会出事：

```
3 节点：L（Leader，term 5）、F、G。F 的日志 1..10 与 L 一致。
① L 发 A：prev=10, entries=[11]
② 12、13 到了，L 又发 B：prev=10, entries=[11,12,13]（也可能是 A 的重传捎带了新条目）
③ 网络乱序，B 先到。F 的日志变成 1..13，回复成功，match=13
④ L 靠 {L, F} 过半提交了 13，并告诉客户端「成功」
⑤ 迟到的 A 这时才到，prev=10 能匹配上
   错误实现：log = log[:11] + [11] → F 只剩 1..11，12、13 被删了
   正确实现：11 已存在且 term 相同 → 跳过；没有冲突 → 不截断，12、13 保留
⑥ 按错误实现，如果 L 此时宕机：只有 L 有 12、13。
   F 和 G 选出新 Leader，已经告诉客户端成功的写就丢了
```

所以，follower 回复过的 match 是一个**承诺**：说了「我有了」，就永远不能收回。

- Leader 端的「只增不减」，保证记账不倒退；
- follower 端的「只有冲突才截断」，保证承诺不被收回。

MIT 6.824 的 Students' Guide 专门强调过这一点：「The *if* here is crucial」。

同样的道理，也解释了为什么 commitIndex 的上限是 `min(leaderCommit, prev + len(entries))`：follower 日志里超出这次 RPC 范围的部分，还没有被这次 RPC 验证过。举个例子：

- F 的 1..10 与 Leader 一致，11..15 是旧任期 3 留下的、没有提交的条目。
- 新 Leader 发来一个心跳：prev=10，entries 为空，leaderCommit=14。
- 如果拿「自己的最后一条」当上限，F 会把旧任期的 11..14 当成已提交去 apply，而这几条和 Leader 的根本不一样。
- 用 prev + 0 = 10 当上限，就是安全的。

### 5. 有了 pipelining，为什么还会自然批量？「单条消息」指什么？

你抓到了我原来那句话的漏洞：「上一轮**发送**还在进行时到达的请求，下一轮一起带走」，在有 pipelining 时是不成立的。窗口没满时，一条提案可以立刻单独成为一条 MsgApp 发出去，网络这一层确实不一定成批。

**批量真正发生在串行的那个资源上，也就是落盘。**

- etcd 的 raft 是一个 Ready 循环：一个 Ready 包含这段时间新增的**所有**日志条目，以及所有要发出去的消息。应用层处理完一个 Ready（写 WAL、fsync），才去取下一个。
- 当前这次 fsync 还在进行时，新来的提案就在内存里排队，下一个 Ready 一次性把它们带走：一次写盘、一次 fsync。这就是 group commit。follower 那边也是同样的机制。
- 另外还有两处也会成批：
  - 传输层会把排队的多条消息合成一次 flush 发出去。
  - 窗口打满、或者 follower 落后时，下一条 MsgApp 会一次带上积压的全部条目（受单条消息大小上限约束）。
- Leader 的发送和它自己的落盘是并行进行的。etcd 源码注释引用的是 Raft 博士论文 10.2.1：Leader 可以一边复制、一边写自己的盘。

**所以 pipelining 和 batching 并不冲突，它们解决的是两种不同的成本：**

- pipelining 让多批数据同时在路上，隐藏的是 RTT；
- batching 让一次 fsync、一个消息头分摊给很多条，摊薄的是固定开销。

单个 Raft 组的吞吐，大致受下面三项里最小的那个限制：

- 每秒 fsync 次数 × 每次带走的条数；
- 窗口 × 单条消息大小 ÷ RTT；
- CPU。

**关于「单条消息」**：「单条消息 1MB」指的是一条 MsgApp 里所有条目的总字节上限，也就是一批。对应 etcd 的 `maxSizePerMsg`，它是软上限，至少会带一条。「窗口 512」指每个 follower 最多同时有 512 条 MsgApp 已发出、未确认，对应 `maxInflightMsgs`。所以可以这样理解：一条消息 ≈ 一批，窗口 = 同时在路上的批数。

顺手算一下：512 × 1MB ÷ 100ms（跨地域 RTT）≈ 5GB/s，根本用不完。这说明跨地域部署主要伤的是延迟，而不是吞吐。这个结论第 7 题会用到。

### 6. 「先做 Leader 转移，再移除旧节点」是什么意思

场景是：你要下线的那台机器，恰好是现任 Leader。

**直接 remove Leader**：它要先把「不包含自己」的新配置提交出去，然后下台；或者像 etcd 那样，发现自己被移除后自行停止。剩下的节点要等一个选举超时（etcd 默认 1 秒），再加上随机化的时间，才能选出新 Leader。这段时间里写不可用。

**先转移，再移除**：执行 `etcdctl move-leader <目标ID>`，过程是这样的：

1. Leader 暂停接收新提案。etcd raft 在转移期间会直接丢弃新提案，返回 `ErrProposalDropped`。
2. Leader 把目标节点的日志补到和自己一样新。
3. Leader 给目标节点发 `TimeoutNow`，目标立刻发起选举。因为它的日志是最新的，所以一定会赢。

这样停写的时间 ≈ 追平日志的时间 + 一个 RTT，而不是一整个选举超时。转移完成后，原来的 Leader 只是一个普通 follower，移除它就是最简单的那种情况。

etcd 自己也是这么做的：`EtcdServer.Stop()` 的第一步就是 `TransferLeadership()`，也就是说优雅停机时会先把 Leader 交出去。滚动升级用的也是同一个套路，比如 TiKV 在重启一台机器之前，会先把这台机器上的 Leader 驱逐走。

### 7. 现实中的部署：同机房还是跨地域？吞吐和延迟怎么权衡

先记住两条物理约束：

- **写延迟的下限 ≈ fsync + Leader 到「凑够过半的那个 follower」的 RTT。** 5 副本时，要看离 Leader 第二近的那台。
- **吞吐基本不受 RTT 影响。** 这是第 5 题那个算术的结论，吞吐主要受磁盘、CPU、带宽限制。但如果客户端是同步地一条一条发，按 Little 定律，并发数 = 吞吐 × 延迟：延迟变成原来的 50 倍，就需要 50 倍的并发才能跑出同样的吞吐。

常见的几种放法：

| 放法 | 能扛住 | 写延迟主要看 | 典型用法 |
|---|---|---|---|
| 同机房 3/5 台 | 单机故障 | fsync（机房内 RTT 只有几百微秒） | etcd 官方建议；K8s 控制面；Chubby / ZooKeeper 这类协调服务 |
| 同城 3 个可用区 | 一个可用区挂掉 | 跨可用区 RTT（个位数毫秒） | 云上最常见的默认方案：Spanner regional、TiDB、CockroachDB 默认配置 |
| 两地三中心 2+2+1 | 一个机房挂掉；扛不住主城市整体挂掉 | 仍是同城 RTT（异地那份只做容灾） | TiDB 官方方案，国内金融行业常见 |
| 3 个地域 | 一个地域挂掉 | 跨地域 RTT（几十到上百毫秒） | Spanner multi-region、CockroachDB 的 REGION 级容灾目标 |

可以调节的旋钮有这些：

1. **把 Leader 放在写请求来的地方。** 比如 TiDB 规定 Leader 只放在主城市，Spanner 有「默认 Leader 地域」。
2. **使用不参与投票的副本。** learner、observer、witness 可以在远端提供读，又不会拉长写入凑过半的路径。
3. **读路径分档：**
   - Lease Read：在 Leader 本地读，没有 RTT。
   - Follower Read：去 Leader 取一次 readIndex，数据从本地读。
   - 有界陈旧读：Spanner stale read、CockroachDB follower read、TiDB stale read 都属于这一类。完全本地读，但不是线性一致的。
4. **Multi-Raft，按数据归属放置。** 用户在哪里，他那部分数据的 Raft 组和 Leader 就放在哪里，例如 CockroachDB 的 REGIONAL BY ROW、TiDB 的 Placement Rules。这样大多数请求的延迟都是本地的，只有少数跨地域的事务需要付出代价。
5. **分层。** 只让元数据/控制面走共识，比如 etcd、ZooKeeper、KRaft 控制器，通常部署在一个地域之内；数据面用 ISR 复制或跨地域异步复制（例如 Kafka MirrorMaker），用「可能丢一点」来换延迟。
6. **超时参数要跟着 RTT 调。** etcd 调优文档的建议是：心跳 ≈ RTT，选举超时 ≥ 10 × RTT。跨地域部署的代价之一，就是故障切换也跟着变慢了。

**一句话总结**：先决定要扛住多大范围的故障——机器、机房、城市还是地域。这决定了副本必须分得多开，也就决定了写延迟的物理下限。吞吐可以靠 pipelining、batching 和 Multi-Raft 基本补回来；延迟补不回来，只能靠放置策略和读路径去绕开。
