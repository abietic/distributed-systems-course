0.1 为什么需要分布式：三堵墙

先回答一个前提问题：既然分布式这么麻烦，为什么不干脆用一台机器？答案是，单机会撞上三堵墙，而且这三堵墙的性质完全不同。

1
容量墙 —— 一台机器装不下
你的数据有 500 TB，单机最大硬盘 30 TB。你的 QPS 是 200 万，单机极限 5 万。这堵墙是物理的：加钱也翻不过去，因为世界上不存在那么大的机器。解法叫 分区 / 分片（Partitioning / Sharding）——把数据切开放到不同机器上。
2
可用性墙 —— 一台机器一定会挂
硬盘年故障率约 1–2%，电源、内存、网卡、机房断电、运维手抖……单机可用性做到 99.9%（年停机 8.7 小时）已经很不错，而 99.99% 单机做不到。这堵墙是概率的。解法叫 复制（Replication）——同一份数据存多份，挂一个还有别的。
3
地理墙 —— 光速是有限的
上海到弗吉尼亚，光在光纤里单程约 60 ms，往返 120 ms，这是物理下限，再多钱也买不到更快。美国用户访问上海的机器一定卡。解法是就近部署多地副本——于是你又回到了复制，而且是跨地域的复制。

注意这三堵墙的解法只有两个词：分片 和 复制。整个分布式系统领域，本质上就是在研究这两件事带来的后果。而"后果"就是这门课剩下的全部内容。

但复制不是免费的——先看一个反直觉现象

很多人以为"多加机器 = 更可靠"。这只在正确使用冗余时才成立。如果你只是把一个单体应用拆成 10 个微服务串行调用，每个服务 99.9% 可用，整条链路的可用性是 0.99910 ≈ 99.0%——你把年停机时间从 8.7 小时变成了 87 小时。拆分服务在没有冗余的情况下会降低可用性。

下面这个计算器让你亲手验证。三种拓扑的含义：

  • 串联：N 个组件全都要活着，系统才可用（无冗余的调用链、微服务链路）
  • 并联：N 个副本任意一个活着就行（只读缓存、无状态服务 + 负载均衡）
  • 多数派 / Quorum：N 个副本中超过一半活着才行（Raft、ZooKeeper、etcd 集群——后面第 3 部分的主角）

0.2 单机世界里你免费拥有的三件事

这是本章最重要的一节。如果你只记住一页，记住这一页。

当你在一台机器上写下面这段代码时，你在无意识地依赖三个假设：

// 单机：一个再平常不过的转账
func Transfer(from, to *Account, amount int) {
    mu.Lock()
    defer mu.Unlock()
    from.balance -= amount        // ← 假设 ③：内存里只有一份余额
    to.balance   += amount
    log.Printf("%v 转账完成", time.Now())  // ← 假设 ①：有一个共同的"现在"
}
// 调用方
Transfer(a, b, 100)   // ← 假设 ②：它要么执行了，要么 panic 了，没有第三种可能
单机免费送你的分布式里发生了什么于是这门课要讲
① 一个共同的"现在"
所有代码读同一个时钟，先发生的事时间戳一定更小		 每台机器有自己的石英晶振，走得快慢不一；NTP 校时会让时钟倒退。你无法用时间戳判断两台机器上事件的先后。 Lamport 逻辑时钟、向量时钟、happens-before 偏序、Google TrueTime、HLC 混合时钟
② 调用只有两种结果
成功 or 失败，且你总能知道是哪种		 网络调用有第三种结果：超时。超时意味着"我不知道"——对方可能没收到、可能执行了但回包丢了、可能还在慢慢执行。 幂等性、去重表、TCC、Saga、两阶段提交、exactly-once 的真相
③ 数据只有一份
写进去立刻能读出来，谁读都一样		 数据被复制成 3 份放在 3 台机器上。写了主副本，从副本还是旧值。两个客户端同时读，看到不同结果。 一致性模型谱系（线性一致 / 顺序一致 / 因果一致 / 最终一致）、CAP、Quorum、共识算法
把这三行刻在脑子里

没有共同的时间 → 顺序问题 → 逻辑时钟与共识
没有确定的结果 → 重复问题 → 幂等与分布式事务
没有唯一的数据 → 一致问题 → 一致性模型与复制协议

你在后面几十小时里学的每一个算法，都可以被归到这三行中的某一行。学到任何新概念时，先问自己：它在赎回哪一件失物？

顺带纠正一个常见误解

很多入门材料说"分布式系统就是把任务分给多台机器并行做"。这描述的是并行计算。分布式系统的定义要苛刻得多，Leslie Lamport 有一句著名的定义：

"分布式系统就是这样一种系统：一台你根本不知道其存在的机器出了故障，会导致你自己的计算机不可用。"
— Leslie Lamport, 1987

关键词是 部分失效（partial failure）。单机程序是"全有或全无"：机器挂了，整个程序一起消失。分布式系统里，一部分节点活着、一部分挂了、还有一部分你不知道死活——而程序必须在这种状态下继续正确工作。部分失效是分布式系统唯一的、也是全部的难点。

0.3 三个不可靠：网络、时钟、进程

上一节的三个假设为什么会崩塌？因为分布式系统建立在三样不可靠的东西之上。

不可靠的网络

你在代码里写 client.Call("Server.Add", args, &reply)，看起来像个函数调用，但底下的网络可以做出五种"恶行"：

恶行现象真实世界的原因
丢包消息发出去，永远没到交换机缓冲区满、网线松动、防火墙丢弃、路由黑洞
延迟消息到了，但晚了 3 秒排队、拥塞、GC 停顿、CPU 争抢、跨洋链路
乱序先发的后到多路径路由、重传
重复同一个消息到了两次底层重传 + 原包其实没丢
分区集群被切成两半，互相不通，但各自内部正常机架交换机故障、跨机房专线中断、BGP 配置错误
TCP 能解决这些吗？

TCP 解决了单条连接内的丢包、乱序、重复（靠序号 + 重传 + 确认）。但它不能解决：连接本身断掉（此时已发送但未确认的数据去向不明）、超时、以及网络分区。TCP 的可靠性止步于连接的边界，而分布式系统的问题恰恰发生在边界之外。这就是为什么应用层还必须自己做幂等和重试。

0.4 时间：没有一个共同的"现在"

你可能觉得"时钟不准"顶多差几毫秒，不是大问题。这个直觉在分布式系统里会害死人。先看两种时钟：

墙上时钟
wall clock
time.Now() / System.currentTimeMillis()。返回"1970 年以来的秒数"，可以转成人类日期。会被 NTP 校准而跳变，甚至倒退。绝不能用来测量时间间隔。
单调时钟
monotonic clock
Go 的 time.Since() / Java 的 System.nanoTime()。只保证"永远向前"，数值本身没有意义。可以测间隔，但不同机器之间毫无可比性。
新手最常犯的两个错

① 用 currentTimeMillis() 的差值测耗时——NTP 一校时，你会得到负数的耗时，或者一个 -3600000 ms 的"超时"。
② 用时间戳比较两台机器上事件的先后——机器 A 的时钟快 50 ms，一个"后发生"的事件时间戳反而更小。基于时间戳的 last-write-wins 会因此静默丢数据（Cassandra 早期最著名的坑）。

石英晶振的典型漂移是每天几十毫秒到几秒；NTP 在广域网上的校准误差通常是 几十毫秒量级。而现代系统里两次操作的间隔可能只有几百微秒。时钟误差比你要区分的时间尺度大好几个数量级——这就是为什么必须发明"逻辑时钟"。

实验 3 · 时钟漂移与顺序倒置
让时间戳给出错误的因果顺序
你要观察的现象

点「运行 / 暂停」让时钟走 20 秒（快钟 A 会跑在前面、慢钟 C 落在后面），然后在几秒内快速依次点 A → B → C 各产生一个事件。表格会同时给出真实发生顺序和按时间戳排序的顺序——被标红的行就是因果倒置：一个后发生的事件，时间戳却更小。
现在想象这三个节点是同一个数据的三个副本，冲突解决策略是"时间戳大的赢"。你刚刚静默地丢了一次写入，而且没有任何日志会告诉你。
注：这里的漂移被夸大了几个数量级（±90 ms/s）以便肉眼观察。真实石英钟的漂移约 10⁻⁵ 量级（每天几秒），但分布式系统要区分的事件间隔常常只有毫秒级——比例关系完全一样，所以问题同样严重。

解法的方向不是"把时钟调准"（做不到，除非像 Google Spanner 那样在每个机房装 GPS 接收器和原子钟），而是放弃物理时间，改用事件之间的因果关系来定义顺序。这就是 Lamport 在 1978 年论文里提出的 happens-before 关系——我们会在 Part 2 详细展开，那是整个领域最优雅的一篇论文。

0.5 分布式系统的原罪：你无法区分"慢"和"死"

现在把网络的不可靠和进程的不可靠放在一起，会得到一个致命的推论。

假设你是节点 A，向节点 B 发了一个请求，等了 2 秒没有回应。B 现在处于什么状态？

可能性 A

B 崩溃了。进程没了，机器断电了，永远不会回复。你应该立刻选一个新的领导者，把 B 的活儿接过来。

可能性 B

B 活得好好的，只是正在经历一次 3 秒的 GC 停顿，或者网络拥塞让回包卡在队列里。它 1 秒后就会恢复，继续以为自己是领导者。

核心结论（请读三遍）

在一个异步网络（消息延迟没有上界）中，「节点崩溃」和「节点很慢」这两件事，从外部观察者的角度看是完全无法区分的。你手上唯一的工具是超时，而超时只能告诉你"我等够久了"，永远不能告诉你"它死了"。

这个结论的代价极高：

  • 超时设短了 → 把活着的节点误判为死亡 → 选出第二个领导者 → 脑裂（split-brain），两个主同时写，数据分叉
  • 超时设长了 → 真的挂了也要等很久才发现 → 可用性下降，用户看到几十秒的卡顿
  • 这不是"调参"能解决的权衡，它是信息论意义上的不可能——这也是 1985 年 FLP 不可能性定理的直觉来源：在完全异步、允许一个节点崩溃的系统里，不存在既保证安全又保证一定终止的共识算法。

Raft、Paxos 这些算法并没有"解决"这个问题，它们做的是把不可避免的风险从"数据错乱"转移到"暂时不可用"——宁可停下来，也不出错。理解这一点，你就理解了共识算法的全部设计动机。

0.6 第三态与幂等性：本章最实用的一节

单机函数调用有两种结果，网络调用有三种：

✓
成功
收到了响应，且响应说成功。你确切知道对方做了。
✗
明确失败
收到了响应，响应说"参数非法"/"余额不足"。你确切知道对方没做。
?
第三态：不确定（indeterminate）
超时、连接被重置、进程崩溃。你不知道对方做了没有。这一态在单机世界里不存在，是分布式编程一切复杂度的源头。

你只有两个选择，而且都不完美

策略做法风险
至多一次
at-most-once		不重试。超时就报失败。可能漏做：用户看到"下单失败"，但订单其实创建了（幽灵成功）。
至少一次
at-least-once		超时就重试，重试到成功为止。可能重做：转账扣两次、订单下两单、邮件发两封。
"恰好一次（exactly-once）"存在吗？

在网络传输层面不存在——两将军问题（下一节）会证明这一点。任何号称 exactly-once 的系统（Kafka 的 EOS、Flink 的精确一次），实际做的都是：at-least-once 传输 + 接收端幂等去重。也就是说，exactly-once 是一个语义（effect）保证，不是一个传输（delivery）保证。这句话面试常考，也是很多线上事故的认知根源。

解法：幂等性（idempotence）

一个操作是幂等的，意思是执行一次和执行 N 次，对系统状态的影响完全相同。

  • SET x = 5 幂等；x = x + 1 不幂等
  • HTTP 的 GET / PUT / DELETE 语义上幂等；POST 不幂等
  • 把不幂等的操作变幂等的标准手法：让客户端生成一个唯一的 幂等键 / idempotency key（UUID 或业务单号），服务端把"键 → 结果"存进一张去重表，同一个键第二次来直接返回上次的结果，不重复执行副作用。Stripe、支付宝、微信支付的 API 都是这么设计的。
// 服务端：把"扣款"变成幂等操作
func Deduct(key string, acct string, amount int) (Result, error) {
    tx := db.Begin()
    defer tx.Rollback()

    // ① 去重表插入，唯一索引在 key 上
    if err := tx.Exec("INSERT INTO dedup(key) VALUES(?)", key); isDup(err) {
        return tx.LoadResult(key), nil   // ← 重复请求，返回上次结果，不再扣款
    }
    // ② 真正的副作用，和 ① 在同一个事务里 —— 这一点至关重要
    tx.Exec("UPDATE accounts SET balance = balance - ? WHERE id = ?", amount, acct)
    tx.SaveResult(key, ok)
    return ok, tx.Commit()
}
为什么去重表必须和业务操作在同一个事务里？

如果分成两步（先写去重表，再扣款），那么在两步之间崩溃会导致：去重表说"做过了"，但钱没扣，重试也会被拦截 → 永久丢失一次操作。反过来先扣款再写去重表，崩溃后重试会扣两次。把两个副作用绑进一个原子操作——这个思路是后面所有分布式事务方案（2PC、本地消息表、事务消息）的共同起点。

0.7 两将军问题：为什么"确认"永远不够

这是分布式领域最古老的思想实验（1975），它证明了一件事：在信道可能丢消息的前提下，两方无法达成确定的共同知识（common knowledge）。

场景：两支军队分别在山谷两侧，只有同时进攻才能获胜，任何一方单独进攻必败。将军之间只能派信使穿过敌占区传信，信使可能被抓（消息丢失）。问：他们能否约定一个共同的进攻时间？

A 发出"凌晨 4 点进攻"。但 A 不敢进攻，因为不知道信使有没有到。于是 B 收到后回一个确认。但 B 也不敢进攻，因为不知道确认有没有到 A 那里——如果确认丢了，A 不会进攻，B 单独进攻就是送死。于是 A 收到确认后再回一个"确认的确认"……这个过程永不终止。

实验 6 · 确认的无限回归
试着让两位将军都敢进攻
你要观察的现象

无论你点多少次，最后一个发消息的人永远不知道对方是否收到，所以他永远不敢进攻。知识层级可以无限加深（"A 知道 B 知道 A 知道…"），但共同知识永远无法达成。
这对工程意味着什么？网络层的"恰好一次投递"在理论上就不存在，不是工程师不够努力。所有实际系统都是在概率上足够好（重试 N 次后失败概率极低）+ 语义上幂等 之间做妥协。分布式事务里的两阶段提交同样受制于此——协调者在发出 commit 后崩溃，参与者就会陷入完全一样的困境。

0.8 故障模型谱系：先说清楚"坏"是怎么个坏法

设计任何分布式算法前，必须先声明它假设了哪种故障模型。模型越弱（假设的坏事越多），算法越复杂、代价越高。

故障模型节点可能怎么坏代表算法 / 容错代价
崩溃-停止
crash-stop / fail-stop		要么正常，要么彻底停机且永不回来。最理想化的模型，教学常用。
崩溃-恢复
crash-recovery		会崩溃，之后可能重启回来，内存丢失，磁盘上的持久化数据还在。Raft / Paxos / ZAB 的模型。需 2f+1 个节点容忍 f 个故障——所以 3 台容 1 台，5 台容 2 台。
遗漏
omission		节点活着，但会丢失部分收发的消息。介于崩溃与拜占庭之间，实践中常被归入崩溃-恢复处理。
拜占庭
Byzantine		节点可能任意行为：说谎、对不同人说不同的话、伪造消息、被黑客控制。PBFT / 区块链共识。需 3f+1 个节点容忍 f 个恶意节点，且需要签名。代价高得多。
为什么拜占庭需要 3f+1 而不是 2f+1？

崩溃模型里，沉默的节点只是"缺席"，剩下的诚实节点意见一致即可。拜占庭模型里，恶意节点会主动投出错误的票。假设 n=3, f=1：诚实节点 A 收到 B 说"进攻"、C 说"撤退"，其中一个在说谎，但 A 无法分辨——2 比 1 的多数无法形成。需要 n ≥ 3f+1，才能保证在扣掉 f 个恶意节点和 f 个可能不可达的节点后，剩下的诚实节点仍构成多数。
工程提示：绝大多数公司内部系统（数据库、消息队列、协调服务）假设的是崩溃-恢复模型，因为机房里的机器不会主动作恶。拜占庭容错主要出现在区块链等去信任场景。这门课的主线是崩溃-恢复模型。

另一组必须区分的词：安全性 vs 活性

安全性 Safety

"坏事永远不会发生。"
例：任何时刻最多只有一个 leader；已提交的数据永不丢失；不会读到不存在的值。
安全性一旦被违反，损害不可撤销（钱已经错扣了）。所以工程上宁可牺牲活性也要保安全性。

活性 Liveness

"好事最终会发生。"
例：请求最终会得到响应；集群最终会选出 leader。
活性被违反只是"暂时不可用"，网络恢复后系统会自愈。注意"最终"没有时限——这正是 FLP 定理攻击的地方。

后面读任何论文或看任何算法，第一件事就是问：它的安全性保证是什么？它在什么条件下才有活性？Raft 论文的整个正确性证明就是围绕五条安全性属性展开的。

0.9 术语速查表

后面每一章都会用到这 20 个词。现在不用背，遇到时回来查。

术语一句话解释常见误解 / 补充
节点 node参与系统的一个独立进程（通常一台机器一个）。关注点是"独立的失败单元"，不是"物理机"。
副本 replica同一份数据在不同节点上的多个拷贝。为了容错和就近读，代价是一致性问题。
分片 shard / partition把大数据集切成互不重叠的小块，分散到不同节点。Kafka 里叫 partition，MySQL 里叫分库分表。解决容量，不解决容错。
主 / 从 leader / follower一组副本中指定一个负责接收写入，其余同步它。也叫 primary/secondary、master/slave。写入串行化的最简单办法。
法定人数 quorum做决定所需的最少节点数，通常是"过半"（N/2+1）。过半的关键性质：任意两个 quorum 必有交集，这保证了新旧决定不会互相矛盾。
脑裂 split-brain网络分区后两边各自选出 leader，同时接受写入，数据分叉。quorum 机制正是为了防止它：少数派凑不齐过半，无法选主。
复制日志 replicated log把所有写操作按顺序记成一个 append-only 的日志，副本按同样顺序重放。整个共识领域的核心抽象。Raft、Kafka、MySQL binlog 全是这个模式。
状态机复制 RSM确定性状态机 + 相同顺序的相同输入 ⇒ 相同的最终状态。"确定性"很重要：日志里不能有 rand() 或 now()。
共识 consensus让一组节点对"下一条日志是什么"达成一致，且决定后不可更改。Paxos / Raft / ZAB 解决的都是这一个问题。
RPC远程过程调用：让网络调用"看起来像"本地函数调用。它看起来像本地调用，这正是它最危险的地方——掩盖了延迟、失败和第三态。
幂等 idempotent执行 1 次和 N 次效果相同。重试安全的前提条件。
第三态请求超时，你不知道对方执行了没有。单机世界不存在的状态。
一致性 consistency多个副本对外表现得像不像"只有一份数据"。注意歧义：CAP 里的 C（线性一致性）和 ACID 里的 C（约束不被破坏）是完全不同的两个概念，这是最常见的术语混淆。
线性一致性 linearizability最强的单对象一致性：系统表现得就像所有操作在某个瞬间原子地、按真实时间顺序发生。直觉版："写完之后，任何人立刻都能读到新值。"代价是每次读写都要走一遍共识。
最终一致性 eventual consistency如果停止写入，所有副本最终会收敛到相同的值。"最终"没有时限保证，中间可以任意乱。它是一个非常弱的保证，弱到几乎没说什么。
因果一致性 causal consistency有因果关系的操作，所有人看到的顺序一致；无关操作的顺序可以不同。实践中的甜点：比最终一致强得多，又不需要全局共识。
可见性 visibility一个写入从"提交"到"能被其他人读到"之间的关系。你路线图里提到的词，它其实是一致性模型在描述的东西。
网络分区 partition集群被切成互不通信的两组，各组内部正常。CAP 里的 P。它是不可选的——分区一定会发生，你只能选分区时保 C 还是保 A。
安全性 / 活性坏事不发生 / 好事最终发生。见 §0.8。
拜占庭 Byzantine节点可能任意作恶，包括说谎。需要 3f+1，代价远高于崩溃容错。

0.11 自测题

先自己想 30 秒再展开。展开前的那 30 秒才是学习真正发生的地方。

1. 把一个单体应用拆成 5 个微服务串行调用，每个 99.9% 可用，整体可用性是多少？这说明了什么？

0.9995 ≈ 99.5%，年停机从 8.8 小时涨到约 43.8 小时。

说明：拆分服务本身会降低可用性。微服务提高的是开发效率和独立伸缩能力，可用性必须靠额外的冗余（多副本 + 重试 + 熔断降级）单独买回来。这是很多团队微服务化后可用性反而下降的直接原因。

2. 单机编程时你免费拥有的三件事是什么？它们各自对应后面哪一类算法？
  • 一个共同的"现在" → 崩塌为顺序问题 → Lamport 时钟、向量时钟、共识（全序广播）
  • 调用只有成功/失败两种结果 → 崩塌为第三态 → 幂等、去重、2PC/TCC/Saga
  • 数据只有一份 → 崩塌为副本不一致 → 一致性模型、Quorum、复制协议

如果你能默写出这三行，这一章的核心目标就达成了。

3. 为什么 etcd / ZooKeeper 集群通常是 3 台或 5 台，而不是 4 台或 6 台？

共识需要过半（quorum = ⌊N/2⌋+1）。3 台的 quorum 是 2，容忍 1 台故障；4 台的 quorum 是 3，也只容忍 1 台故障。4 台没有提升容错能力，却多了一台会坏的机器，还多了一份网络往返成本——所以偶数节点在容错上是纯亏。

至于为什么很少超过 5 台：每次写入都要等过半节点确认，节点越多延迟越高（尾延迟被最慢的那台拖累）。3/5 是容错能力与写延迟之间的甜点。需要更多读能力时，用 learner / observer 这种不参与投票的只读节点扩展。

4. 客户端调用超时了。它能得出"服务器没有执行这个请求"的结论吗？

不能。超时只说明"在我等待的时间内没收到响应"，它无法区分四种情况：请求丢了 / 请求到了但服务器还在处理 / 服务器执行完了但响应丢了 / 服务器崩溃了（崩溃前可能已执行）。

这就是第三态。工程上的正确做法不是去猜，而是让猜错也无害：把操作设计成幂等的，然后放心重试。

5. Kafka / Flink 号称支持 exactly-once，这和两将军问题矛盾吗？

不矛盾，因为它们保证的是处理效果恰好一次（effectively-once），不是投递恰好一次。

实现方式是 at-least-once 传输 + 接收端去重/事务：Kafka 给每个 producer 分配 PID 和单调递增的 sequence number，broker 端据此丢弃重复；配合事务把"写数据"和"提交 offset"绑成一个原子操作。网络层面的 exactly-once 投递在理论上不存在——两将军问题证明了这一点。

6. 什么是脑裂？quorum 机制为什么能防止它？

网络分区把集群切成两半后，两边各自认为对方挂了，各自选出 leader 并接受写入，数据分叉且无法自动合并。

quorum 要求当选 leader 必须获得超过半数节点的选票。5 个节点被切成 3+2 两组时，只有 3 那一组能凑齐 3 票，2 那一组永远选不出 leader——因为任意两个过半集合必然有交集，不可能同时存在两个 quorum。少数派会主动停止服务（牺牲可用性保安全性），这正是 CAP 中"选 CP"的含义。

7. 用 System.currentTimeMillis() 的差值来测量一段代码的耗时，可能出什么问题？

它是墙上时钟，会被 NTP 校准而跳变甚至倒退。你可能得到负数耗时，或者一个突然多出几小时的"超时"。闰秒和虚拟机迁移也会造成同样问题。

正确做法：测间隔用单调时钟——Java 的 System.nanoTime()，Go 的 time.Since(start)（Go 的 time.Time 内部同时带有单调读数，Sub 会自动使用它）。墙上时钟只用于"显示给人看"和"记录日期"，绝不用于测量和排序。

8. CAP 里的 C 和 ACID 里的 C 是同一个东西吗？

完全不是，这是分布式领域最常见的术语混淆。

  • CAP 的 C = 线性一致性（linearizability），描述多副本对外是否表现得像单副本，是一个系统层面的属性。
  • ACID 的 C = 一致性约束不被破坏（比如外键约束、余额非负），是应用层面的属性，本质上由应用代码保证，数据库只是提供了 A（原子性）和 I（隔离性）来帮忙。

Brewer 自己后来也承认 CAP 的表述有误导性——"三选二"的说法尤其糟糕，因为 P 根本不是可选项。

9. 崩溃容错需要 2f+1 个节点，拜占庭容错需要 3f+1，为什么多了 f 个？

崩溃模型下，故障节点只会"沉默"，不会给出错误信息。诚实节点之间不会互相误导，所以只要 f+1 个诚实节点（即 2f+1 中扣掉 f 个崩溃的）就能形成多数。

拜占庭模型下，恶意节点会主动投出矛盾的票，而且可能对不同节点说不同的话。要在扣掉 f 个可能不响应的节点后，剩下的 n−f 个响应中仍能保证诚实票占多数（即 n−f−f > f），推出 n > 3f，即 n ≥ 3f+1。

10. 为什么幂等去重表必须和业务操作在同一个事务里？分开写会怎样？

如果分成两个独立步骤，中间崩溃会产生两种坏结果：

  • 先写去重表，再做业务：崩在中间 → 去重表说"做过了"，但业务没做，客户端重试会被拦截 → 永久丢失一次操作。
  • 先做业务，再写去重表：崩在中间 → 业务做了但没记录，客户端重试会再做一次 → 重复扣款。

只有把两者放进同一个原子事务，才能保证"记录了就一定做了，做了就一定记录了"。这个"把两个副作用绑成一个原子操作"的思路，是 Part 4 里本地消息表、事务消息、Outbox 模式的共同起点。

11. Lamport 说"一台你根本不知道其存在的机器出故障，会导致你的计算机不可用"——这句话在强调什么？

强调 部分失效（partial failure）。单机程序是全有或全无；分布式系统里总有一部分组件是坏的、一部分是慢的、一部分死活未知，而系统必须在这种混合状态下继续正确工作。

它同时也在讽刺一种设计倾向：把远程调用包装得和本地调用一模一样（早期的 RPC 和 CORBA），会诱导开发者忘记网络的存在。好的分布式 API 应该让失败可见，而不是把它藏起来。

12. 【综合】设计一个"用户点击按钮领取优惠券，每人限领一次"的接口，在分布式环境下要考虑哪些本章讲过的问题？

至少这几层：

  1. 第三态：用户点了按钮，App 超时。用户会重复点击。所以接口必须幂等——用 用户ID + 活动ID 作为天然幂等键（比随机 UUID 更好，因为它表达了业务上的唯一性），配唯一索引。
  2. 原子性：「插入领取记录」和「扣减库存」必须在同一事务内，否则崩溃会造成超发或少发。
  3. 并发：两个请求同时到达两台应用服务器。不能用"先 SELECT 查有没有领过，再 INSERT"——这是典型的检查后行动竞态。要靠数据库唯一索引，让冲突在存储层被拒绝。
  4. 不能用时间戳做判重：两台机器时钟不同步，"谁先到"不可靠。
  5. 如果用了分布式锁：注意锁的持有者可能因 GC 停顿超过锁的 TTL 而失去锁却不自知（§0.5 的原罪）——这时需要 fencing token，Part 6 会详细讲。更稳妥的做法是根本不依赖分布式锁，而依赖数据库的唯一约束。
  6. 可见性：如果读走从库，用户领完立刻刷新可能看到"未领取"（复制延迟）。需要"读己之写"保证——领取后的这次读走主库，或用会话粘性。
