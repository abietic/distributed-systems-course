Part 1 · Time, Order & Causality

没有全局时钟，怎么说"这件事在那件事之前"

你在第 0 章的自测里说对了一句关键的话：单调时钟能防止"时间明明向后却回拨"，而这会影响可见顺序和超时剔除。这一章把那句话拆成两半——超时剔除属于单调时钟的领域，已经解决了；可见顺序不属于任何一种物理时钟，它需要一个全新的东西。

用途用哪种时钟为什么
测耗时、超时、心跳、限流窗口单调时钟只关心"过了多久"，绝对值无意义，必须免疫 NTP 跳变。nginx 2018 年才把 ngx_current_msec 改成 CLOCK_MONOTONIC；Redis 6.2 才引入 getMonotonicUs()。
TTL / 过期时间 / 定时任务墙上时钟语义就是"到某个绝对时刻作废"，必须跨进程重启、跨主从一致。所以 Redis 的 key 过期至今仍用 mstime()，这是对的。
判断两台机器上事件的先后两种都不行需要逻辑时钟。这一章就是解这一行的。
这一章你会带走什么
  • happens-before 偏序——一套不依赖任何时钟就能定义"先后"的语言，1978 年 Lamport 发明，至今是全领域的通用词汇
  • Lamport 时钟与它的根本局限（只能单向推断），以及为什么它仍然够用于分布式互斥
  • 向量时钟——唯一能精确判定"并发"的工具，以及它 O(N) 的代价
  • 亲手复现 last-write-wins 静默丢数据，再用向量时钟把它抓出来
  • HLC 与 Spanner TrueTime：工业界怎么把物理时间重新拿回来
  • Lab 1：Go 与 Java 各实现一遍两种逻辑时钟，并写出冲突检测器

1.1 三种时钟，三种世界观

墙上时钟

time.Now()
System.currentTimeMillis()

回答"现在几点"。可以转成人类日期、可以跨机器传递。会跳变、会倒退，两台机器上的读数不可比。

单调时钟

time.Since(t0)
System.nanoTime()

回答"过了多久"。保证只向前，但起点是任意的（通常是开机时刻），跨机器毫无意义——把 nanoTime 的值发给另一台机器是纯粹的 bug。

逻辑时钟

Lamport 时钟
向量时钟

回答"谁可能影响了谁"。和物理时间完全无关，只由消息收发定义。跨机器可比，而且这是它存在的唯一目的。

为什么不能"把时钟调准就行了"

NTP 在广域网上的校准误差通常是几十毫秒；同机房内用 PTP 能做到微秒级，但需要专门硬件。而现代系统里两个需要区分先后的操作，间隔可能只有几十微秒。误差比要区分的尺度还大，这个方向根本走不通。Google 的 Spanner 是唯一认真走这条路的——他们在每个机房装了 GPS 接收器和原子钟，把误差压到个位数毫秒，然后用等待把剩下的误差消化掉（§1.7）。绝大多数系统买不起这个方案。

1.2 happens-before：不用时钟定义先后

Lamport 1978 年那篇论文的核心洞察极其简单：我们其实并不真正关心"物理上谁先发生"，我们关心的是"谁可能影响了谁"。而"可能影响"这件事，完全可以只用消息收发来定义。

定义关系 a → b（读作 "a happens-before b"），由三条规则递归生成：

1
同一进程内的顺序：如果 a 和 b 在同一个进程里，且 a 在 b 之前执行，那么 a → b。
单机内部的顺序是确定的，这一条几乎是白送的。
2
消息的因果：如果 a 是"发送消息 m"，b 是"接收消息 m"，那么 a → b。
这是唯一一条跨进程的规则。信息只能通过消息流动，所以因果也只能通过消息流动。
3
传递性：如果 a → b 且 b → c，那么 a → c。

然后是最关键的一步——定义"并发"：

如果既不满足 a → b，也不满足 b → a，就称 a 和 b 并发，记作 a ∥ b。

注意"并发"在这里不是"物理上同时发生"的意思。两个事件可能相隔三个小时，只要期间没有任何消息把它们串起来，它们就是并发的——因为谁都不可能影响谁，谁排在前面都无所谓。

这是偏序，不是全序 —— 本章最容易被跳过的一句话

全序（total order）意味着任意两个元素都能比较大小，比如整数。happens-before 是偏序（partial order）：有些事件对之间根本没有关系。
这不是理论缺陷，恰恰是它的价值所在：它诚实地告诉你哪些顺序是真实存在的、哪些是你自己脑补的。一个只按时间戳排序的系统会给你一个虚假的全序，让你以为一切都有确定顺序；happens-before 会明确指出"这两件事没有先后，你必须自己决定怎么办"——而这正是冲突检测的基础。

1.3 Lamport 逻辑时钟

happens-before 是一个关系，不是一个数。Lamport 接着问：能不能给每个事件贴一个整数 L(e)，让这个数尊重因果关系？算法只有三行：

1
每个进程维护一个计数器 L，初始为 0。
2
任何本地事件（含发送）前：L = L + 1，把 L 作为该事件的时间戳。发送消息时把 L 一起带上。
3
收到携带 Lm 的消息时：L = max(L, Lm) + 1，作为接收事件的时间戳。
// Go：完整实现只有这么多
type Lamport struct{ mu sync.Mutex; t uint64 }

func (l *Lamport) Local() uint64 {          // 本地事件 / 发送
    l.mu.Lock(); defer l.mu.Unlock()
    l.t++
    return l.t
}
func (l *Lamport) Recv(remote uint64) uint64 { // 接收
    l.mu.Lock(); defer l.mu.Unlock()
    if remote > l.t { l.t = remote }
    l.t++
    return l.t
}

它保证了什么，没保证什么

✓ 保证（时钟条件）

a → b ⟹ L(a) < L(b)

如果 a 因果先于 b，那 a 的时间戳一定更小。逆否命题才是实际用法：如果 L(a) ≥ L(b)，那么 a 绝不可能影响 b。

✗ 不保证（根本局限）

L(a) < L(b) ⇏ a → b

看到 3 < 7，你无法断定前者影响了后者——它们可能完全并发，只是各自计数器碰巧到了那个值。Lamport 时钟只能证伪，不能证实。

回到实验 1 去验证这一点：找两个来自不同进程、之间没有任何消息路径的事件，你会看到它们的 Lamport 值一定不同（除非碰巧相等），但比较面板会明确告诉你它们是并发的。这个信息差就是向量时钟要填补的空缺。

那 Lamport 时钟还有什么用？

有一个非常实际的用途：构造一个任意但一致的全序。用二元组 (L(e), 进程ID) 按字典序排序，就得到了一个全序，而且它兼容因果序（不会把因果关系排反）。所有节点独立计算这个排序，结果完全一致。

  • Lamport 在原论文里用它实现了分布式互斥锁：所有请求按 (L, pid) 排队，谁排第一谁拿锁。不需要中心协调者。
  • 很多系统用它给操作打上"全局唯一且单调"的编号，比如事务 ID、消息序号。
  • 注意这个全序是任意的——对并发事件它随便选了一个顺序。只要所有人选的一样，系统就能保持一致，哪怕这个顺序和物理现实不符。一致比正确更容易达到，也常常已经足够。

1.4 向量时钟：把"并发"变成可检测的

Lamport 时钟把每个事件压缩成一个整数，信息丢失了。向量时钟不压缩：N 个进程的系统里，每个事件带一个长度为 N 的向量，第 i 位记录"我所知道的进程 i 已经走到第几步"。

1
进程 i 维护向量 V，初始全 0。
2
本地事件（含发送）：V[i] = V[i] + 1。发送时把整个 V 带上。
3
收到向量 Vm：先逐位取最大 V[k] = max(V[k], Vm[k])（对所有 k），再 V[i] = V[i] + 1。

比较规则（这里是全部的精髓）：

条件结论直觉
∀k: V(a)[k] ≤ V(b)[k] 且至少一位严格小于a → bb 知道 a 知道的一切，还多知道一些 ⇒ b 在 a 之后
反过来同理b → a
两个方向都不成立
即 a 有某位更大，b 也有某位更大		a ∥ b（并发）各自知道对方不知道的事 ⇒ 谁都没影响谁 ⇒ 这就是一次冲突
逐位相等同一个事件
关键升级：这次是充要条件

a → b ⟺ V(a) < V(b)
Lamport 时钟只有 ⟹，向量时钟有 ⟺。这意味着向量时钟能精确检测出并发，而这正是所有多主复制系统（Dynamo、Riak、CouchDB）赖以工作的基础：检测到并发就说明有冲突，必须保留双方或交给应用合并，而不是闷头丢掉一个。

代价与两个常见混淆

  • 空间 O(N)：每个值都要带一个和节点数等长的向量。节点数上千时不可接受。工程上的缓解：只给写入过的副本记条目、定期修剪陈旧条目（Riak 的做法）、或者改用点式版本向量（dotted version vector）。
  • 向量时钟 vs 版本向量：两者算法几乎一样但用途不同。向量时钟给事件编号（每个事件递增），版本向量给数据副本的版本编号（每次写入递增）。数据库里说的通常是后者，但大家习惯都叫向量时钟。知道有这个区分就够了。
  • 它不解决冲突，只发现冲突。发现之后怎么办有三条路：交给应用（Dynamo 的 siblings，购物车做并集）、用 CRDT 保证自动合并（Part 2）、或者干脆用共识把并发消灭掉（Part 3）。

1.5 last-write-wins：一个静默的数据杀手

现在把前面所有东西接到你的实际经验上。LWW（最后写入者获胜）是最简单的冲突解决策略：给每个写入打上时间戳，冲突时保留时间戳大的那个。Cassandra 默认就这么干，很多自研的多机房同步方案也这么干。

它的问题是：它把一个偏序问题当成全序问题来解。两个并发写入本来没有先后，LWW 强行用物理时间戳给它们排序——而物理时间戳恰恰是不可靠的。结果就是：

后写的数据被判成"旧值"丢弃，没有任何日志，没有任何报错

用户点了保存，界面显示成功，数据库里也确实写进去了，几秒后被另一个副本的同步覆盖掉。这是分布式系统里最难排查的一类故障，因为它不留痕迹。

那到底什么时候可以用 LWW？

可以用，但要满足条件——把这三条当成一张检查表：

  • 写入是幂等且可丢的：比如"最后一次心跳时间"、"最近一次在线状态"。丢一次无所谓，下一次覆盖就好。
  • 同一个 key 极少并发写：单一写入者，或者天然按用户分片，冲突概率本就趋近于零。
  • 时间戳由单一来源生成：比如统一由某个 leader 或发号器打戳，而不是各个客户端用自己的本地时钟。这一条能消掉大部分风险。

反过来，凡是"累加"、"追加"、"集合增删"语义的数据，用 LWW 一定会丢东西——购物车、点赞列表、余额、计数器。这类数据要么用 CRDT（Part 2 会实现一个），要么走共识串行化（Part 3）。

1.6 混合逻辑时钟 HLC：把物理时间赎回来

逻辑时钟解决了因果，但丢掉了一样东西：可读性和可比性。Lamport 值 84213 对应现实中的什么时刻？不知道。你没法问"给我 10:00 那一刻的数据快照"，也没法给日志排序时和监控图表对齐。

HLC（Hybrid Logical Clock，2014）的想法很聪明：时间戳是二元组 (l, c)，l 尽量贴着物理时钟走，c 是一个小计数器，只在物理时钟"不够用"时才递增。

1
本地事件 / 发送：l' = max(l, pt)（pt 是当前物理时钟）。若 l' == l 则 c++，否则 c = 0。
2
收到 (lm, cm)：l' = max(l, lm, pt)。
若 l' == l == lm 则 c = max(c, cm) + 1；若 l' == l 则 c++；若 l' == lm 则 c = cm + 1；否则 c = 0。

性质：(l,c) 按字典序比较，满足 Lamport 时钟条件（a→b ⟹ HLC(a) < HLC(b)），同时 l 与真实物理时间的偏差有界（不超过时钟误差上限）。它是单调的——即使物理时钟回拨，l 也绝不倒退，回拨期间靠 c 递增撑住。

CockroachDB、YugabyteDB、MongoDB（4.0 起的因果一致性会话）都用 HLC。它的甜点位置是：不需要原子钟，也能同时拿到因果正确性和大致可用的物理时间。

1.7 TrueTime：Google 花钱买来的确定性

Spanner 想要的东西比因果一致更强，叫外部一致性（external consistency）：如果事务 T1 在现实世界中先于 T2 提交（哪怕两者毫无因果关系、由地球两端的客户端发起），那么系统给出的时间戳必须满足 ts(T1) < ts(T2)。逻辑时钟做不到这一点——它对并发事件不做承诺。

Google 的解法是承认时钟有误差，然后把误差显式建模出来。TrueTime 的 API 不返回一个时刻，而返回一个区间：

TT.now() → [earliest, latest]   // 真实时刻一定落在这个区间内
                                // 区间宽度 ε 通常是 1~7 ms

底层靠每个机房里的 GPS 接收器 + 原子钟（两种独立失效模式的时间源互相校验），把 ε 压到个位数毫秒。然后是关键的一招——commit wait：

commit wait：用等待换确定性

事务选定提交时间戳 s = TT.now().latest 之后，不立刻返回给客户端，而是主动等待，直到 TT.now().earliest > s——也就是等到"真实时间确定已经越过 s"为止。这段等待通常就是 ε（几毫秒）。
等待之后，任何在此之后开始的事务拿到的时间戳一定大于 s。时钟误差被转化成了一段可控的延迟。这是我最喜欢的一个工程权衡：不去消灭不确定性，而是给它标价，然后买单。

代价也很直白：每个事务的提交延迟增加约 2ε，而且你需要在每个机房部署 GPS 天线和原子钟。对绝大多数团队，HLC 是那个够用且免费的答案。但理解 TrueTime 的价值在于——它划出了这条路的终点：物理时钟路线能走多远，取决于你愿意为 ε 花多少钱。

1.8 通向共识：从"知道顺序"到"约定顺序"

这一章解决的是观测问题：给定已经发生的事件，我怎么判断它们的因果关系。但还有一个更难的问题没解决——决策问题：怎么让所有节点事先约定一个共同的顺序，而不只是事后各自分析。

这个更强的目标叫全序广播（total order broadcast），也叫原子广播：

  • 可靠投递：消息不丢；如果一个节点收到了某条消息，所有正常节点最终都会收到。
  • 全序投递：所有节点以完全相同的顺序收到所有消息——包括那些互相并发的消息。
这条线索会一直贯穿到 Part 3 和 Part 5

全序广播和共识在计算上是等价的（可以互相归约）。而"把所有写操作以相同顺序投递给所有副本"正是状态机复制的定义。所以：
全序广播 ≡ 共识 ≡ 复制日志 ——三个名字，同一件事。
Kafka 的分区内有序、ZooKeeper 的 ZAB、Raft 的日志复制，全都是这件事的不同实现。你在 Part 3 手写 Raft 的时候，写的就是一个全序广播协议。

为什么这一章的逻辑时钟不够？因为 Lamport 时钟给出的全序 (L, pid) 是事后算出来的——每个节点必须先收到所有相关消息才能确定排序，而在异步网络里你永远不知道"是不是还有一条更早的消息在路上"。要真正确定下来，就必须有节点做出决定并让所有人接受，而这需要多数派投票。这就是共识算法存在的理由。

1.9 自测题

老规矩：先自己想 30 秒再展开。

1. 用一句话说清 happens-before 和"物理上先发生"的区别。

happens-before 描述的是"可能影响"，物理先后描述的是"时钟读数大小"。

两个事件可以相隔三小时却是"并发"的（期间没有任何消息把它们串起来，谁都不可能影响谁）；也可以物理上几乎同时，却有明确的 happens-before 关系（一个是发送、一个是接收）。因果关系只沿着消息流动。

2. 为什么说 happens-before 是偏序而不是全序？这是缺陷还是特性？

因为存在互相无法比较的事件对（并发事件）。

这是特性。偏序诚实地标出了"哪些顺序是真实的，哪些是你脑补的"。用时间戳强行造出的全序看起来更方便，但那个顺序里有一部分是虚构的——LWW 静默丢数据正是因为把虚构的顺序当真了。发现"这两件事没有先后"本身就是一条重要信息，它等价于"这里有一个冲突需要处理"。

3. L(a) < L(b) 能推出 a → b 吗？L(a) ≥ L(b) 能推出什么？

前者不能。Lamport 时钟只保证 a → b ⟹ L(a) < L(b)，反向不成立——两个并发事件的 Lamport 值也可能一大一小。

后者能，而且这才是它的实际用法：由逆否命题，L(a) ≥ L(b) ⟹ a 不 happens-before b，也就是a 绝不可能影响 b。Lamport 时钟只能证伪，不能证实。

4. 向量时钟 V(a)=[2,1,0]、V(b)=[1,3,0]，两个事件是什么关系？

并发。a 的第 0 位更大（2 > 1），b 的第 1 位更大（3 > 1）——两个方向都不满足"逐位 ≤"，所以互不 happens-before。

直觉：a 知道进程 0 走了 2 步而 b 只知道 1 步；反过来 b 知道进程 1 走了 3 步而 a 只知道 1 步。各自都知道对方不知道的事，说明它们之间没有信息流动过。在数据库里，这意味着一次真实的写冲突。

5. Cassandra 用 last-write-wins。什么情况下这是安全的，什么情况下一定会丢数据？

相对安全：写入幂等且可丢（心跳时间、在线状态）、同 key 极少并发写、时间戳由单一来源生成（leader 或发号器，而非各客户端本地时钟）。

一定丢：语义是"累加 / 追加 / 集合增删"的数据——购物车、点赞列表、余额、计数器。这类数据的两次并发写在语义上应该合并，而 LWW 只会二选一。解法是 CRDT（Part 2）或走共识串行化（Part 3）。

6. 向量时钟这么强，为什么工业界不到处都用？

空间成本 O(N)：每个数据版本都要携带一个与节点数等长的向量。几十个节点还行，上千个节点就不可接受了；而且节点会上下线，向量里会堆积陈旧条目。

缓解手段：只为实际写过的副本保留条目、定期修剪、或改用点式版本向量（DVV）。更重要的是另一条路——如果系统本来就用共识把所有写串行化（单 leader 复制），那就根本不存在并发写，也就不需要检测冲突。向量时钟是"允许多主写入"这个设计选择的配套成本。

7. HLC 相比纯 Lamport 时钟多给了什么？相比纯物理时钟又多给了什么？

相比 Lamport：时间戳的高位贴着物理时间走，误差有界。于是你可以做"读取 10:00 那一刻的快照"这种时间范围查询，日志也能和监控图表对齐。纯 Lamport 值是个没有现实含义的整数。

相比物理时钟：保证单调 + 满足时钟条件（a→b ⟹ HLC(a)<HLC(b)）。物理时钟会因 NTP 回拨而倒退，也不尊重因果。HLC 用一个额外的小计数器把两边的优点都拿到了，这是它被 CockroachDB / MongoDB 采用的原因。

8. Spanner 的 commit wait 在等什么？为什么必须等？

事务选定提交时间戳 s = TT.now().latest 后，等待直到 TT.now().earliest > s——也就是等到"真实时间已确定越过 s"。

必须等，是因为要保证外部一致性：任何在本事务提交之后才开始的事务，拿到的时间戳必须更大。如果不等就返回，下一个事务可能在时钟误差窗口内拿到一个更小的时间戳，造成"后提交的事务时间戳更早"。本质上是把时钟不确定性 ε 转换成了约 2ε 的提交延迟——不消灭不确定性，而是给它标价买单。

9. 为什么逻辑时钟不足以实现全序广播？

因为 Lamport 全序 (L, pid) 是事后算出来的。一个节点收到时间戳为 7 的消息时，无法确定是否还有一条时间戳为 5 的消息正在路上——异步网络里没有延迟上界。要安全地投递，它必须等到确认"所有更早的消息都已到达"，而这个条件永远无法在有限时间内确定。

要真正定下来，必须有人做出决定并让多数派接受。这就是共识。全序广播 ≡ 共识 ≡ 复制日志，三者可以互相归约。

10. 【综合】多机房部署，用户在北京改了昵称，几乎同时在上海改了头像，两地各写各的副本再互相同步。用 LWW 会怎样？用向量时钟会怎样？你实际会怎么设计？

LWW（整行覆盖）：两次写各自携带本地时间戳，同步时时间戳大的整行获胜——另一个字段的修改被连带丢弃。用户会看到"我明明改了头像，怎么没了"。这是多机房 LWW 最典型的事故。

向量时钟：判定为并发，产生两个 siblings，把冲突暴露给应用层。应用可以按字段合并（昵称取一边、头像取另一边），因为这两个字段本来就不冲突。

实际设计，按优先级：
① 缩小冲突单元——按字段级而非整行做 LWW，昵称和头像各自独立打戳。绝大多数"多机房覆盖"事故靠这一条就消失了。
② 把用户数据按归属地分片，同一个用户的写入永远路由到同一个主机房。没有并发写就没有冲突，这是最省事的办法。
③ 真的需要多地同时可写时，用向量时钟 + 字段级合并，或者对能表达成 CRDT 的字段（集合、计数器）用 CRDT。
④ 强一致要求高的部分（比如账户余额）走共识，接受跨地域的延迟。
注意①和②都不是"更好的算法"，而是"把问题设计掉"。这在工程上通常比引入向量时钟更划算。
