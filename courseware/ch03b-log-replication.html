复制到过半，不等于可以提交

上一节结束时我问了你一个问题：Leader 把日志复制给过半 follower 并收到确认，这条日志就能提交了吗？你答"可以了"。几乎所有人第一次都这么答——包括 Raft 的作者，早期草稿里就是这么写的，后来发现了反例才补上限制。这一节的核心就是那个反例。

正确的规则

Leader 只能通过计数副本来提交自己当前任期的日志条目。
前任任期留下的条目，即使已经复制到过半节点，也不能直接提交——只能等当前任期的某条日志被提交之后，靠日志匹配性质间接提交。

为什么要有这条奇怪的限制？因为存在一个执行序列，让一条"已经复制到过半"的前任日志之后被彻底覆盖掉。如果你在它复制到过半时就宣布提交、回复客户端"成功"，那这个成功就是假的——已提交的数据被推翻，安全性直接破产。§3.13 会让你一格一格把它走一遍。

3.10 日志长什么样

Raft 的日志是一个只追加的数组。每个条目三样东西：

type Entry struct {
    Index int   // 在日志中的位置，从 1 开始（0 号位是哨兵）
    Term  int   // ★ 这条日志是在哪个任期被 Leader 创建的
    Cmd   any   // 要交给状态机执行的命令，比如 SET x=3
}

Term 字段是全部安全性的关键，它不是给人看的元数据，而是参与算法判断的核心。记住这个直觉：index 说的是"排第几"，term 说的是"这是谁那一届写的"。两个节点的日志在同一个 index 上如果 term 也相同，Raft 就能断定它们从头到这里完全一样——这就是下一节的日志匹配性质。

已提交 committed

这条日志已经复制到过半节点，且满足 §3.12 的提交规则。
承诺：它永远不会丢失、永远不会被改变，无论后面发生多少次选举、多少次崩溃。Leader 只有在这之后才能回复客户端"成功"。

已复制但未提交

日志已经写进了某些节点的磁盘，但还不满足提交条件。
它随时可能被新 Leader 截断丢弃。客户端此时收到的只能是"处理中"或超时——绝不能是"成功"。

这两者的区别就是 Part 0 的第三态在 Raft 内部的样子。客户端发来的请求走到"已复制未提交"就崩溃了的话，它的命运是未定的——可能之后被提交，也可能被丢弃。所以客户端仍然需要幂等键和重试，Raft 并不能让你免掉 Lab 0 的那些功课。

3.11 日志匹配性质：两个字段的魔法

Leader 通过 AppendEntries 把日志推给 follower。这个 RPC 的关键在于它带了两个"上文"字段：

AppendEntries(
    term         // Leader 的任期
    leaderId
    prevLogIndex // ★ 紧挨着新条目之前的那条日志的 index
    prevLogTerm  // ★ 那条日志的 term
    entries[]    // 要追加的新条目（心跳时为空）
    leaderCommit // Leader 的 commitIndex
)

Follower 收到后做一件事，只有一件：

一致性检查

检查自己的日志在 prevLogIndex 位置上，term 是不是等于 prevLogTerm。
不相等（或那个位置根本没有日志）就拒绝，一个字节都不接受。
相等才追加，并且如果新条目和已有条目在某个 index 上冲突（term 不同），删掉该位置及其之后的全部日志，再追加。

为什么这一个检查就够了

它导出了 Raft 最漂亮的一条性质：

日志匹配性质 Log Matching Property

① 如果两个节点的日志在同一个 index 上的条目有相同的 term，那么这两条日志存储的是同一条命令。
② 而且，这两个节点从开头到这个 index 的所有日志完全相同。

① 成立，是因为 Leader 在一个任期内、一个 index 上只会创建一个条目，且日志条目一旦写下就不会移动位置。

② 是归纳出来的：一致性检查相当于一次归纳步骤。最初空日志平凡匹配；每次 AppendEntries 成功，都意味着 follower 在 prevLogIndex 处与 Leader 一致——由归纳假设，从头到 prevLogIndex 全都一致；追加之后，到新位置也一致。于是一个只看一个位置的局部检查，维持住了整条日志的全局一致。

这条性质的实用价值极大：要判断两条日志是否相同，只需比较最后一条的 (index, term)，不必逐条对比。上一节选举规则里"日志至少和自己一样新"的那个比较，就是靠它才能只看一对数字。

3.12 提交规则：什么时候才能对客户端说"成功"

Leader 为每个 follower 维护两个指针：

nextIndex[i]
乐观猜测：下一条要发给节点 i 的日志位置。当选时初始化为「自己日志长度 + 1」，被拒绝就回退。
matchIndex[i]
保守事实：已确认节点 i 与自己一致的最高位置。只在 AppendEntries 成功时前进。

然后提交规则是（Raft 论文 §5.4.2，逐字翻译）：

存在一个 N > commitIndex，使得
① 过半的 matchIndex[i] ≥ N，并且
② log[N].term == currentTerm　← 就是这一条，你上一节答漏了
则令 commitIndex = N。

条件①是直觉的"过半确认"。条件②才是这一节的主角：只有当前任期创建的日志，才能靠数副本数来提交。

那前任任期的日志怎么办？靠间接提交：一旦当前任期的某条日志 N 被提交，由日志匹配性质，N 之前的所有条目在过半节点上也必然一致，于是它们同时被提交。所以新 Leader 上任后通常会立刻追加一条空的 no-op 日志，用它把前任遗留的日志一次性带过提交线——这是工业实现的标准做法（etcd、TiKV 都这么干）。

"复制到过半"保证的是数据不会因为少数节点故障而丢失，它不保证这条日志会赢得未来的选举。
S5 之所以能在阶段 (d) 当选，是因为它的日志 (term=3) 比 S2/S3 的 (term=2) 更新——选举规则比的是 (lastLogTerm, lastLogIndex)，先比 term。所以一条 term=2 的日志哪怕复制到了三个节点，也挡不住一个只有一条 term=3 日志的节点当选。
Raft 的修补方式很克制：不改选举规则，只加一条提交限制。只要 Leader 不把前任的日志宣布为"已提交"，它被覆盖就不构成安全性违规——因为从来没人被告知它成功了。

3.14 五条安全性属性

Raft 论文的正确性证明就是围绕这五条展开的。它们不是并列关系，而是层层依赖：

① 选举安全性
Election Safety
一个任期内至多一个 Leader。
靠"过半票 + 每任期一票 ⇒ 两个过半集合必相交"。3-A 已证。
② Leader 只追加
Leader Append-Only
Leader 从不覆盖或删除自己的日志，只追加。
这条是实现约定，但它让后面几条的推理变得可能——日志的"历史"在 Leader 这里永远单调。
③ 日志匹配
Log Matching
若两条日志在某 index 上 term 相同，则该 index 及之前的全部条目都相同。
靠 AppendEntries 的一致性检查归纳得到。§3.11 已证。
④ Leader 完整性
Leader Completeness
如果一条日志在任期 T 被提交，那么它一定出现在所有任期 > T 的 Leader 的日志里。
这是全部五条里最重要的一条，也是唯一需要真正证明的一条。见下方。
⑤ 状态机安全性
State Machine Safety
如果某个节点在 index i 上应用了一条命令，那么没有任何节点会在 index i 上应用不同的命令。
这是对外的最终承诺——所有副本的状态机走出完全相同的轨迹。它是 ③+④ 的推论。

Leader 完整性的证明（反证法）

假设它不成立：日志条目 e 在任期 T 被提交，但存在某个任期 U > T 的 Leader L_U 的日志里没有 e。取最小的这样的 U。

1
e 在任期 T 被提交 ⟹ 它被复制到了过半节点（记这个集合为 A）。
2
L_U 当选 ⟹ 它获得了过半节点的选票（记为 B）。
3
两个过半集合必然相交 ⟹ 存在节点 v ∈ A ∩ B。（又是这一条。它在 Raft 里出现了三次。）
4
v 持有 e（因为 v ∈ A），并且投票给了 L_U（因为 v ∈ B）。
投票规则要求：L_U 的日志至少和 v 一样新。
5
比较 (lastLogTerm, lastLogIndex)：
• 若 L_U 的 lastLogTerm 等于 v 的，则 L_U 日志至少一样长，由日志匹配性质它必然包含 e —— 矛盾。
• 若 L_U 的 lastLogTerm 更大，设为 W（T ≤ W < U）。那么任期 W 的 Leader 创建了那条日志。由 U 的最小性，任期 W 的 Leader 必须包含 e。而 Leader 只追加不删除，且日志匹配性质保证 L_U 从任期 W 的 Leader 那里复制来的日志包含 e —— 也矛盾。

两种情况都矛盾，故假设不成立。∎

注意这个证明里用到的三块砖：过半集合必相交、投票时比较日志新旧、提交规则限制在当前任期。少任何一块，证明就断了——而 §3.13 的 Figure 8 演示的正是"抽掉第三块砖"的后果。这三条不是三个独立的设计，是一个整体。

3.15 冲突回退：从 O(n) 轮 RPC 降到 O(任期数) 轮

朴素做法里，AppendEntries 被拒绝时 Leader 把 nextIndex 减 1 再试。如果 follower 落后一万条，就要一万轮 RPC——每轮一个网络往返，跨机房时就是几十秒。

论文在 §5.3 的脚注里给了一个优化：让 follower 在拒绝时带上更多信息，让 Leader 一次跳过整个冲突任期。etcd 和 TiKV 用的是它的变体：

// Follower 拒绝时返回：
conflictTerm  int  // prevLogIndex 处自己的日志的 term（若该位置为空则为 -1）
conflictIndex int  // 自己日志中 conflictTerm 的第一条的 index
                   // （若该位置为空，则为自己的日志长度 + 1）

// Leader 收到后：
if conflictTerm == -1 {
    nextIndex[i] = conflictIndex          // follower 太短，直接跳到它的末尾
} else if hasTerm(leaderLog, conflictTerm) {
    nextIndex[i] = lastIndexOfTerm(leaderLog, conflictTerm) + 1
    // Leader 也有这个任期 ⇒ 分歧点在这个任期之后
} else {
    nextIndex[i] = conflictIndex          // Leader 没有这个任期 ⇒ 整段都要覆盖
}

3.15b 附加一节：高任期的节点回归时会发生什么

这一节回答一个非常好的问题：3-A 里少数派节点的任期会疯涨，分区恢复后它会不会当选？ 选举到底看不看 commitIndex？少数派的僵尸 Leader 也一直在 append，这跟 Figure 8 是不是一回事？

先钉死一件事：选举从来不看 commitIndex。投票时比较的只有 (lastLogTerm, lastLogIndex)。 commitIndex 是节点本地的一个进度指针，它不参与任何投票判断——事实上一个节点根本无法验证另一个节点报上来的 commitIndex 是否可信。

然后要把少数派里的两类节点分开看，它们的行为完全不同：

① 普通的少数派节点
follower → candidate → 超时 → 再来
它不停超时、不停 term++，但它从不追加日志——只有 Leader 才写日志，而它永远当不上 Leader。
所以：任期疯涨，日志冻结。
恢复后它的高任期会逼现任 Leader 退位（因为任期比较优先于一切），触发一次不必要的选举——但它自己赢不了，因为它的日志落后。这就是「有破坏力但没有危险」。
② 少数派里的僵尸 Leader
3-A 场景③里遇到的那个
它自认为还是 Leader，会继续接受客户端请求并追加日志——但这些日志永远提交不了（拿不到过半确认）。
所以：任期冻结（它是 Leader，不会自己涨任期），日志疯长。而且这些日志的 term 是旧的那个任期。
这才是真正值得琢磨的情况。

僵尸 Leader 回归时，它那条「更长但更旧」的日志会赢吗

比较规则是字典序 (lastLogTerm, lastLogIndex)，先比 term。所以答案取决于多数派那边有没有产生过更高任期的日志：

多数派新 Leader 的状态僵尸能赢吗为什么
已经追加并提交了自己任期的日志不能新 Leader 的 lastLogTerm 更大，僵尸的旧 term 一比就输——哪怕僵尸的日志长十倍。
刚当选，还没写过任何自己任期的日志可能能两边 lastLogTerm 相同（都是旧任期），此时比长度，僵尸的日志更长 ⇒ 它更"新"。
第二行看起来危险，其实是安全的 —— 而且这正是 no-op 日志的价值

即使僵尸赢了，也不违反任何安全性属性：它的日志是所有已提交条目的超集（它在分区前就有全部已提交内容，之后只是往后追加）。 它当选后会把那些"悬而未决"的条目一并复制出去并提交——这不是数据损坏，只是让一批原本命运未定的日志最终生效了。
但这个窗口仍然有实际代价：它会让集群多做一次无谓的 Leader 切换。解法就是 §3.12 提过的 no-op——新 Leader 一当选立刻追加一条空日志， 它的 lastLogTerm 瞬间变成当前任期，第二行那种情况的窗口直接关闭。
所以 no-op 不只是"帮前任日志过提交线"，它同时也在"堵住旧 Leader 回来抢位子的缝"。一石二鸟。

它和 Figure 8 是同一件事吗？不是，但共用同一块地基

Figure 8 问的是：一条已提交的日志会不会被覆盖？（答案：如果提交规则不加限制，会。）
这一节问的是：一个日志落后/陈旧的节点能不能当选？（答案：不能，除非两边 lastLogTerm 相同。）
两者的共同地基是同一条比较规则——(lastLogTerm, lastLogIndex) 先比 term。 Figure 8 里 S5 能赢正是因为它的 term 更大（3 > 2）；这里僵尸赢不了正是因为它的 term 更小。同一把尺子，量出两个方向的结论。

关于 Lab 3-A 的一个坦白

Lab 3-A 的代码没有实现「日志至少一样新」这条投票条件——因为那一节的模型里根本没有日志。 我在 3-A §3.6 把它列进了选举规则，却没在代码里落实，也没有标注这个简化。
后果比"行为不一样"严重得多。Lab 3B-5 用三组对照把它测了出来（各 40 次试验）：

恢复后由谁当选① 完整 Raft② 关掉日志检查③ 多数派分区期间没写入
多数派节点（日志更新）401516
少数派节点（日志陈旧）02524
安全性违反0250

②里那 25 次不只是"选错了人"，是真的丢了数据——陈旧节点当选后会用自己的旧日志覆盖别人已提交的条目。 所以 3-A 的模拟器请当作"选举流程的动画演示"来看，不要把它的分区恢复行为当成真实 Raft。

③ 是最微妙的一列，值得单独说：如果分区期间多数派一条写入都没有，两边日志一模一样—— 此时少数派节点根本不"陈旧"，它当选完全合法、也毫无危害（安全性违反 = 0）。
所以准确的说法是「日志真的落后的节点赢不了」，而不是「少数派节点赢不了」。 而真实系统里 ③ 这种窗口几乎不存在，因为新 Leader 一当选就追加 no-op，lastLogTerm 立刻抬到当前任期。

3.16 工业实现里的差异

话题论文里的做法工业实现
no-op 日志论文只说"提交限制在当前任期"，没强制要求 no-op。几乎都加：新 Leader 上任立刻追加一条空日志，用它把前任遗留的条目一次性带过提交线，避免"前任日志迟迟提交不了"的窗口期。etcd、TiKV、RocketMQ DLedger 都是。
批量与流水线一次 AppendEntries 发一批 entries。再加流水线：不等上一批的响应就发下一批（乐观地推进 nextIndex），把吞吐从「1 RPC/RTT」提到「N RPC/RTT」。出错再回退。这是 Raft 能达到高吞吐的关键工程手段。
写盘时机论文要求日志持久化后才响应。可配：fsync 每条（最安全最慢）、批量 fsync、或异步刷盘（快但断电可能丢已"提交"的数据）。很多"用了 Raft 还是丢数据"的事故出在这里，不在算法。
并行复制Leader 并行发给所有 follower。相同。但注意提交延迟由第 ⌈N/2⌉ 快的节点决定——不是最快也不是最慢。所以一个慢节点在 5 副本里无害，在 3 副本里致命。
只读优化论文提出 ReadIndex 与 Lease Read。etcd 默认 ReadIndex（安全，一次心跳往返的代价）；TiKV 默认 Lease Read（更快，依赖时钟漂移有界）。这是 3-C 的内容。
一个真实世界的教训

Raft 的正确性证明假设"日志一旦持久化就不会丢"。而现实里 write() 返回 ≠ 数据落盘，fsync 也可能因为磁盘固件、虚拟化层、云盘缓存而说谎。
Jepsen 测出的很多"共识系统丢数据"，根因都在存储层而非共识层——算法是对的，只是它站在的地基不是它以为的那个。这也是 Part 6 混沌工程与 Jepsen 那一章要讲的：验证一个系统，必须连它的假设一起验证。

3.17 自测题

先自己想 30 秒再展开。

1. 用一句话说清日志匹配性质，以及它为什么能从一个"只看一个位置"的检查里得到。

性质：若两条日志在同一 index 上的条目 term 相同，则该 index 及之前的全部条目都相同。

怎么来的：AppendEntries 的一致性检查就是一次归纳步骤。空日志平凡匹配（基础情形）；每次 AppendEntries 成功，都证明 follower 在 prevLogIndex 处与 Leader 一致，由归纳假设从头到那里全一致，追加后到新位置也一致（归纳步骤）。局部检查维持了全局不变量——这是整个 Raft 里最优雅的一处设计。

2. 一条日志复制到过半节点，能提交吗？给出完整的规则。

不一定。提交需要同时满足两个条件：
① 过半的 matchIndex[i] ≥ N；
② log[N].term == currentTerm——只能提交当前任期创建的条目。

前任任期的条目只能间接提交：等当前任期的某条日志被提交后，由日志匹配性质它之前的条目也随之提交。工业实现通常让新 Leader 立刻追加一条 no-op 日志，用它把前任遗留的条目一次性带过提交线。

3. Figure 8 里，S5 凭什么能在阶段 (d) 当选？它的日志明明比 S1/S2/S3 短。

因为选举规则比的是 (lastLogTerm, lastLogIndex) 的字典序——先比 term，term 相同才比长度。

S5 最后一条日志是 term=3，S2/S3 最后一条是 term=2。3 > 2，所以 S5 的日志"更新"，尽管它更短。于是 S2/S3/S4 都愿意投票给它。
这不是 bug，是刻意的：term 更大意味着"见过更晚的 Leader"，这个信息比长度更能反映谁掌握了更新的集群状态。代价就是 Figure 8 这个反例——所以才需要提交限制来补。

4. 如果去掉"只能提交当前任期日志"这条限制，会发生什么？描述具体后果。

Figure 8 的阶段 (c) 里，S1 把 term=2 的日志复制到了 S1/S2/S3（过半），按朴素规则就提交了，并回复客户端"成功"。

然后 S1 崩溃，S5 靠 term=3 的日志当选（阶段 d），它的 AppendEntries 会覆盖掉 S2/S3 上那条 term=2 的日志。
后果：一条已经向客户端确认成功的数据凭空消失。状态机安全性被破坏——不同节点会在同一个 index 上应用不同的命令。这是分布式系统里最严重的一类故障，因为客户端已经基于"成功"做了下游动作（发货、扣款、通知）。

5. Leader 完整性的证明用了哪三块砖？
  1. 任意两个过半集合必然相交——所以"持有已提交日志的集合"和"给新 Leader 投票的集合"一定有共同节点。
  2. 投票时比较日志新旧——那个共同节点持有已提交的日志，它只会投给日志不比自己旧的 candidate。
  3. 提交限制在当前任期——保证"已提交"这个标签不会贴在一条可能被覆盖的日志上。

抽掉任何一块证明就断了。这三条不是三个独立的设计选择，是一个整体。

6. Leader 会不会删除自己的日志？follower 呢？

Leader 永远不会（Leader Append-Only 属性）。它只追加。这让"日志的历史"在 Leader 视角下永远单调，后面几条安全性属性的推理才成立。

Follower 会：当 AppendEntries 里的新条目和自己已有条目在某 index 上 term 冲突时，删除该位置及其之后的全部日志再追加。
被删掉的一定是未提交的条目——这由 Leader 完整性保证：已提交的条目必然存在于当前 Leader 的日志里，所以不会与 Leader 的内容冲突，也就不会被删。

7. 朴素回退（每次 -1）最坏要多少轮 RPC？快速回退好在哪？

朴素回退最坏 O(日志长度) 轮——follower 落后一万条就是一万个网络往返。跨机房时可能几十秒，期间该 follower 完全无法追上，相当于集群少了一个副本。

快速回退把复杂度降到 O(冲突任期数)：follower 拒绝时带上 conflictTerm（分歧点处它自己的 term）和 conflictIndex（该 term 的第一条），Leader 据此一次跳过整个任期。因为一个任期内的日志要么全对要么全错，逐条试是纯粹的浪费。
实际系统里日志可能有几万条但只跨越几个任期，所以这个优化通常把几万轮降到个位数。

8. Raft 集群里，一次写入的提交延迟由哪个节点决定？

由第 ⌈N/2⌉ 快的 follower 决定——不是最快的，也不是最慢的。Leader 需要凑齐过半（含自己），所以要等到第 ⌊N/2⌋ 个 follower 响应。

实用推论：
• 3 副本：需要 1 个 follower 响应。任何一个节点变慢都直接拖慢整体（另一个可能也慢）。
• 5 副本：需要 2 个 follower 响应，可以容忍最慢的 2 个。一个慢节点在 5 副本里几乎无害，在 3 副本里可能致命。
这也解释了为什么跨地域部署 Raft 要小心：如果 3 个副本里有 2 个在远端机房，每次写入都要付一次跨地域 RTT。

9. "我们用了 Raft，fsync 关掉了因为太慢" —— 这句话的风险是什么？

Raft 的正确性证明有一个前提假设：日志一旦持久化就不会丢失。关掉 fsync 就是直接违反这个假设。

后果：一个节点响应了 AppendEntries（Leader 据此认为该副本已持有日志），但那条日志只在 page cache 里。节点断电重启后日志消失，而 Leader 可能已经据此把日志提交并回复了客户端。凑齐过半的那些副本里，可能有节点其实什么都没存下来 —— 已提交的数据就此丢失。
算法是对的，只是它站的地基不是它以为的那个。Jepsen 测出的很多"共识系统丢数据"根因都在这里。真要提速，正确做法是批量 fsync（攒一批一起刷）而不是关掉它。

10. 【综合】5 节点集群，Leader 追加了一条日志并复制到 3 个节点（含自己），然后崩溃。这条日志的命运有几种可能？

取决于这条日志是当前任期的还是前任任期的，以及 Leader 崩溃前有没有推进 commitIndex。

情况 A：它是当前任期的，且 Leader 已推进 commitIndex 并回复了客户端
→ 它必然存活。由 Leader 完整性：任何未来 Leader 都必须包含它（持有它的 3 个节点构成过半，任何当选者必须从中拿到票，而投票要求日志不比投票者旧）。这是 Raft 给出的承诺。

情况 B：它是当前任期的，但 Leader 还没来得及推进 commitIndex
→ 命运未定。新 Leader 若来自那 3 个节点，日志保留（并会被新任期的 no-op 带过提交线）；若来自另外 2 个节点——不可能，因为它们日志更旧拿不到过半票。所以实际上大概率保留，但客户端从未收到成功，所以 Raft 不欠它什么。

情况 C：它是前任任期的
→ 就是 Figure 8 的场景，可能被覆盖。正因如此，Raft 禁止 Leader 把它宣布为已提交。

对客户端的实际含义：收到"成功" ⟹ 数据一定在（情况 A）；收到超时 ⟹ 第三态，可能在也可能不在（情况 B/C）。所以客户端仍然需要幂等键——Raft 消除的是"副本之间不一致"，不是"客户端不知道自己成功没有"。Lab 0 那些功课一节都免不掉。
