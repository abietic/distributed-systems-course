Raft 附录：教程通常不讲的那几件事

3-A 到 3-C 已经把 Raft 讲完整了。但几乎所有 Raft 教程——包括我前三章——都留下了三个洞，而这三个洞恰好是把 Raft 用对与用错的分界线。

①
「提交了」不等于「读得到」
Raft 有四个 index，不是一个。commitIndex 和 lastApplied 之间那个窗口，是所有「刚写完就读不到」类线上故障的源头。ReadIndex 的第三步才是答案，而大多数文章只讲前两步。
②
Quorum 读写和 Raft 是两个世界
都在说「过半」，但 W+R>N 的 quorum 写不是 Raft 的日志 append。把 Part 2 学的东西往 Part 3 上套，会得出一堆看似合理实则荒谬的结论。
③
配置是鸡生蛋问题
成员列表存在日志里，可要复制日志得先知道成员是谁。冷启动怎么破这个环、配置何时生效、增减节点会不会触发选举——这三件事错一件就是线上脑裂。
这一章的性质

前三章是算法，这一章是算法与系统之间的接缝。Raft 论文里这些内容分散在第 6、7、8 节和博士论文里，被绝大多数二手教程丢掉了——而线上事故恰恰长在接缝上。

3.24 一次写的完整生命周期：Raft 的四个 index

先把一个最常见的误解摆出来：「Raft 提交了这条日志」和「客户端能读到这个值」是两件事，中间隔着一步，而那一步是异步的。

一条客户端写请求在 Leader 上要走完四个阶段，每个阶段对应一个 index：

index含义持久化？能被回滚吗
lastLogIndex已 append 到本地日志的最后一条是（log[]）能。未提交的尾巴随时可能被新 Leader 截断覆盖——3-B 的 Figure 7 就是在演示这个。
matchIndex[i]Leader 记的「第 i 个 follower 已复制到哪」否（Leader 上的易失状态）不适用。它是 Leader 的记账，新 Leader 上任会全部重置为 0 重新试探。
commitIndex已被过半复制、永不回滚的最后一条否（可推导）不能。这就是「提交」的定义。
lastApplied已交给状态机执行的最后一条否（可推导）不能，但会滞后——这是关键。

它们的大小关系永远是：

lastLogIndex  >=  commitIndex  >=  lastApplied
那个窗口

commitIndex 和 lastApplied 之间的区间，是「已经保证不丢、但还没生效」的数据。
apply 是后台线程在做的（要执行命令、写存储引擎、可能还要落盘），所以这个窗口永远存在，只是大小随负载波动。
如果你在这个窗口里直接读状态机，你读到的是过去。

于是 ReadIndex 是三步，不是两步

3-C 里我把 ReadIndex 说成「读之前发一轮心跳确认自己还是主」——那是简化的。完整版：

1
readIndex := commitIndex
记下当前的提交点。前提条件：Leader 必须在本任期内已经提交过至少一条日志，否则 commitIndex 可能还没推到该在的位置。这就是 §3.25 的 no-op。
2
发一轮心跳，收到过半响应
确认「我此刻仍是合法 Leader」，从而确认 readIndex 确实是全集群的提交点，而不只是我自己以为的。这一步防的是僵尸 Leader（3-C）。
3
等到 lastApplied >= readIndex，再读状态机
这一步就是把「日志的版本」和「状态机的版本」对齐。没有它，前两步做得再对也没用——你确认了自己是 Leader、确认了提交点是 7，然后去读一个只重放到 5 的状态机。

第 1、2 步保证 readIndex 这个数字是对的；第 3 步保证 你读的那份数据追上了这个数字。少任何一步都不是线性一致。

commit 与 apply 分开带来的红利：截断永远不需要 undo

follower 截断冲突日志时，被删掉的只可能是未提交的条目（etcd 的实现里，冲突一旦落在已提交范围内直接 panic）。而状态机只 apply 已提交的条目——所以状态机从没见过被截断的东西，什么都不用撤销。
这也是 Raft 状态机不需要 undo log 的原因。对比 InnoDB：它的数据页会先被未提交事务改掉，所以必须有 undo。

那不做检查直接读，读到的是什么？

状态机里永远是某个已提交前缀的结果：不会脏、不会回滚，只可能旧。所以直接本地读给你的是一个一致但不保证新的快照——这本身就是一个有用的级别（etcd 的 --consistency=s）。
三步检查买的是另一个东西：读能看到「在它发起之前已经返回成功的所有写」——这才是线性一致。
客户端在不同 follower 间切换做本地读，还可能先看到 index 10、再看到 index 7——Part 2 的「单调读」异常。

3.25 no-op：新 Leader 上任的第一件事

这条规则藏在 Raft 论文第 8 节的一句话里，但它是 Figure 8 那条限制的直接后果——你在 3-B 已经推过一半了。

回忆 3-B 的提交规则：

// Leader 只能提交当前任期的日志条目；
// 旧任期的条目只能靠「被当前任期的条目带着一起提交」而间接提交。
if log[N].term != currentTerm { continue }

现在看新 Leader 刚当选的那一刻。它的日志里可能有一大段已经复制到过半、但 commitIndex 没标记的旧任期条目——上一任 Leader 复制完就崩了，还没来得及推进 commitIndex 并广播。

新 Leader 想提交它们吗？想。能直接提交吗？不能，Figure 8 那条限制不让。于是形成一个尴尬的僵局：

僵局

新 Leader 的 commitIndex 停在一个偏小的位置，而且如果没有新的写入进来，它会一直停在那里。
此时如果有客户端来读：readIndex := commitIndex 拿到的是那个偏小的值 ⇒ 第 3 步等的是一个过时的目标 ⇒ 读到旧数据，而且 ReadIndex 的前两步都完美通过了。

解法一行字：新 Leader 当选后立刻在自己的任期里 append 一条空的 no-op 条目并复制出去。

no-op 顺带办成的三件事
  1. 推进 commitIndex。no-op 是当前任期的条目，可以直接提交；它一提交，前面所有旧任期条目被顺带提交（提交是前缀性的）。
  2. 让读安全。commitIndex 到位后，readIndex 才是真的。
  3. 探明 follower 的日志。复制 no-op 的过程顺便完成了所有 follower 的 nextIndex 回退试探（3-B 的冲突回退）。
还有第四件（3-C 的补丁）

单节点成员变更有一个 2015 年才被发现的坑：新 Leader 必须先提交一条自己任期的日志，才能发起新的成员变更。否则它可能基于一个尚未提交、后来被回滚的配置做决策。
no-op 同时把这个前提也满足了。
所以 etcd/TiKV 里 Leader 一上任必发 no-op，不是优化，是正确性要求。

no-op 还没提交时来了读请求怎么办？

先等 no-op 提交，再走 ReadIndex 三步。etcd raft 的做法是把这类读挂起排队：

// Postpone read only request when this leader has not committed any log entry at its term.
if !r.committedEntryInCurrentTerm() {
    r.pendingReadIndexMessages = append(r.pendingReadIndexMessages, m)
    return nil
}

本任期第一条提交后再放行。也有实现选择直接拒绝、让客户端重试——两种都安全，区别只在延迟。绝不能做的是拿一个还没到位的 commitIndex 去凑合。
勘误：上一版 Lab 3D-2 写的是「etcd/TiKV 会拒绝服务读」，etcd 实际是排队。

3.26 Quorum 读写 ≠ Raft 日志复制

Part 2 讲了 W+R>N，Part 3 讲了「过半复制才算提交」。它们都在说「过半」，于是很自然会问：quorum 写是不是就是 Raft 的日志 append？

不是。它们属于两个不同的设计世界，底层用的是同一条数学事实，但用法完全相反。

Dynamo 式 Quorum（Part 2）Raft（Part 3）
谁能接受写任何副本（无 Leader，或者说人人都是协调者）只有 Leader
写有全局顺序吗没有。并发写各写各的，产生多个并存版本有。每条日志一个唯一递增 index
冲突怎么办甩给读端：向量时钟 / LWW / CRDT / 应用层合并不会有冲突——Leader 在写入前就定好了序
读要干什么读 R 个副本，自己比较版本、合并、可能还要写回修复读 Leader 一个（加一次确认）就够
「过半」保证什么读集合 ∩ 写集合 ≠ ∅ ⇒ 至少碰到一个持有最新值的副本任意两次成功操作（选举/提交）的参与集合必相交 ⇒ 新 Leader 必持有全部已提交日志
一致性最终一致（可调）线性一致
代表系统Dynamo、Cassandra、Riak、Voldemortetcd、Consul、TiKV、CockroachDB
把差别压成一句话

Dynamo 的 W 说的是「有 W 个副本收下了我发的这个值」——但它们收下的各自是什么并不受约束。
Raft 的过半说的是「有过半节点的 index=5 这个位置，放着同一条 entry」——这是日志匹配性质给的，强得多。
前者是数量的保证，后者是内容与位置的保证。

那 Raft 里有没有「quorum 读」这个东西？

没有。Raft 不需要去读过半副本再比较——读一个 Leader 就够了，因为 Leader 按定义持有全部已提交日志（Leader 完整性）。
ReadIndex 里那一轮心跳看起来像 quorum 读，但它读的不是数据，是「我还是不是 Leader」这一个 bit。数据一个字节都不用从 follower 拿。
这个区别决定了两者的带宽开销差着数量级。

3.27 读到底能不能不走 Leader

Raft 论文的「强 Leader」（strong leader）是定义性的，不是「还没来得及优化读」：

规则一
日志只从 Leader 单向流向 follower
规则二
客户端的所有写都必须经过 Leader

为什么必须这样？因为 3-B 的日志匹配性质（两个日志在同一 index 有同一 term ⇒ 此前全部相同）建立在「只有 Leader 追加」之上。一旦允许 follower 自己接写，这条性质当场破产，而 Raft 的整套安全性证明都架在它上面。

Raft 是用限制换可理解性。Paxos 允许任意节点提议，代价是要处理乱序 chosen 留下的空洞，难懂得多——这正是 Raft 论文开篇声明的设计目标：understandability。

读的四个档位

方式在哪读怎么保证不读到旧值代价线性一致？
本地读Leader不保证0否（3-C 实验里 25/25 全脏）
ReadIndexLeader心跳确认 + 等 apply 追平1 RTT，不写日志是（etcd 默认）
Lease ReadLeader租约未过期 + 等 apply 追平0，但依赖时钟是（前提：时钟漂移有界）
Follower ReadFollower向 Leader 要 readIndex，再等自己 apply 追平1 RTT（去 Leader 要）是
Follower Read 到底省了什么

它不省那一轮确认 RTT——一致性保证仍然来自 Leader 的那次确认。
它省的是 Leader 的数据传输与状态机读取开销：大结果集不必从 Leader 的网卡出去，Leader 的 CPU 也不用去翻存储引擎。对「读多写少 + 单次读结果大」的负载，这个收益很可观；对「读小 key」的负载，收益接近零。
另外要区分：etcd 的 --consistency=s（serializable read）不走 readIndex，它是明确放弃线性一致换延迟的选项，和这里说的 Follower Read 不是一回事。
为什么叫 serializable 却更弱？可串行化和线性一致根本不在一条轴上：前者只要求「等价于某个串行顺序」，后者要求「符合真实时间」。从本地读一个已提交前缀，满足前者、不满足后者。两者都满足的叫 strict serializability。etcd 官方 benchmark 里，线性一致读 141,578 QPS / 5.5ms，serializable 读 185,758 QPS / 2.2ms——差的就是那一轮确认。

论文第 8 节本身就讨论了 read-only 优化（ReadIndex 与 lease），Follower Read 是其上的工程扩展——所以它既不是「论文里的」，也不是「某家的私货」。

3.28 配置：从哪来、何时生效、会不会触发选举

① 配置是从 Leader 下发的吗？是。

成员配置 C_new 就是一条特殊的日志条目，走完全相同的 AppendEntries 路径复制出去。没有第二套通道。

而且它存的不只是「节点 id 的集合」，是 id → 地址 的映射：

{ "type": "config",
  "voters": {
    "n1": "10.0.1.10:2380",
    "n2": "10.0.1.11:2380",
    "n3": "10.0.1.12:2380" },
  "learners": {} }

这直接回答了「机器怎么互相访问到」：地址是配置的一部分，Raft 自己不做服务发现。DNS SRV、K8s Service 这些只是帮你生成那份初始列表。

连回 3-C：为什么快照必须包含配置

配置存在日志里 → 快照会截断日志 → 如果快照不含配置，节点重启后不知道同伴是谁、地址是什么，连选举都发不出去。
这就是 3-C 里 InstallSnapshot 要带 config 的原因，现在它有了完整的来龙去脉。

② 反直觉：配置一收到就生效，不等提交

论文原文：a server always uses the latest configuration in its log, regardless of whether the entry is committed。

为什么不能等提交？因为会死循环：

要提交 C_new  →  得先知道「过半」是几个
「过半」是几个  →  取决于当前生效的是 C_old 还是 C_new
当前生效的是哪个  →  取决于 C_new 提交了没有   ← 回到第一行

Raft 的选择是立即采用，代价是这条配置条目可能被新 Leader 覆盖回滚（节点又退回 C_old）。之所以敢这么干，正是因为单节点变更保证了 C_old 与 C_new 的任意两个过半集合必相交——回滚期间也不可能出现两个 Leader。这就是你在 3-C 推过的那个不等式在兜底。

勘误 · 上面是论文的做法，etcd 走的是另一条路

etcd raft 的 README 原话：membership change "takes effect when its entry is applied, not when it is added to the log (so the entry is committed under the old membership instead of the new)"，并说明这在安全性上是等价的。它的代价是另一条规则：Leader 日志里只要还有未提交的配置变更，新的配置变更一律不接受（一次只能有一个在途）。
所以死循环是这样被打破的：用旧配置提交新配置，提交并 apply 之后才切换。两种做法都安全；读源码时别被「一收到就生效」带偏。

③ 增减机器会触发重新选举吗？默认不会

配置变更本身不触发选举，Leader 继续是 Leader，只是它算「过半」时用的数变了。两个例外：

例外 1 · 被移除的是 Leader 自己

论文的做法是：Leader 在 C_new 提交之后才 step down。
有意思的是这期间它在管理一个不包含自己的集群——复制日志、算过半时不把自己算进去。
它退位后，新集群才会选举。

例外 2 · 被移除的节点捣乱

被移出配置的节点收不到心跳了，会超时、自增 term 发起选举——term 更高会把现任 Leader 打下来，可它不在配置里，永远选不上，严重时反复发生。论文把它叫 disruptive servers。
解法：PreVote 先问一轮「如果我选你会投吗」，不实际自增 term；CheckQuorum 刚收到过 Leader 心跳的节点直接忽略投票请求。

勘误：上一版这里写成了「新节点捣乱」。新节点的问题是可用性（追日志期间可能拖住提交，所以要先当 learner），不是捣乱——etcd 启动新成员时不带任何初始配置，它连自己是不是投票成员都不知道，不会发起选举。

一个常见的错误推理

「{A,B,C} → {A,B,C,D}，过半从 2 变成 3，所以会触发重新选举。」
前半句对，后半句错。过半数确实变了，但现任 Leader 只是从「等 2 个 ack」改成「等 3 个 ack」，它的身份没有任何变化。
过半数变化 ≠ 需要重新选举。Leader 的合法性来自任期和选票，不来自集群规模。

④ 冷启动：怎么破这个鸡生蛋的环

配置存在日志里，可要复制日志得先知道配置。Raft 的答案是：初始配置不能从日志来，必须从外部给。工程上有两条路。

路径 A · 静态引导（static bootstrap）。每个节点启动时用参数写死完整成员列表。以 etcd 为例：

etcd --name infra0 \
  --initial-advertise-peer-urls http://10.0.1.10:2380 \
  --initial-cluster infra0=http://10.0.1.10:2380,infra1=http://10.0.1.11:2380,infra2=http://10.0.1.12:2380 \
  --initial-cluster-state new \
  --initial-cluster-token my-etcd-token
参数作用
--initial-cluster名字 → peer URL 的映射。「有几台机器」从这里数出来，「怎么访问到」也从这里来。
--initial-cluster-statenew = 我在创建一个新集群；existing = 我在加入一个已存在的集群（重启节点，或先 member add 再启动的新节点）。用错会造出第二个集群。
--initial-cluster-token集群标识。防止你同时搭多套配置相同的集群时，节点互相串台认错了亲。
--initial-advertise-peer-urls本节点对外广播的 peer 地址，必须和别人 --initial-cluster 里写的那一项完全一致。
运维踩坑重灾区

这些 --initial-* 参数只在 data dir 为空的首次启动时生效。集群一旦跑起来，成员信息就存进 data dir（在日志/快照里）了，后续重启从本地状态读，--initial-cluster 被完全忽略。
改配置文件不会改变集群成员。要增删成员只能走 member add / member remove；要换 IP 只能走 member update。
data dir 丢了的成员，不要用原来的身份重启：etcd 文档要求先 member remove、再 member add 一个新成员。原因见实验 4 的 D1/D2——同 token 同成员列表算出来的是同一个集群 ID，用 state=new 重启不是「建新集群」，而是「冒充旧成员」。

路径 B · 单节点引导 + 动态加入。先起一台「成员只有我自己」的集群——它一个人就是过半，立刻选自己当 Leader——然后一台一台 member add（生产上先加成 learner，追平后提升）。TiDB 的 PD、Consul 常用这个模式，好处是不需要提前知道最终拓扑，适合弹性伸缩场景。

3.29 Raft log 不是 redo log

两者都是 WAL（write-ahead log，先写日志再改数据），但它们解决的根本不是同一个问题。

Raft LogInnoDB redo log
解决什么多台机器之间就「操作顺序」达成一致单台机器崩溃后不丢已提交事务
内容逻辑命令（SET x=1），必须是确定性的物理/物理逻辑：「表空间 5 第 137 页 offset 92 改成 0x2A」
谁会读它所有副本的状态机，每台都要重放一遍只有本机崩溃恢复时读
能重放到别的机器吗能——这就是它存在的全部意义不能，页号只对本机的数据文件有意义
顺序标识index，跨机器一致LSN，只在本机有意义
怎么截断快照（snapshot）checkpoint（把脏页刷下去）
丢了会怎样Leader 完整性破产，已提交数据可能消失崩溃后丢掉最近已提交的事务
「确定性」这条比看起来要命

Raft log 里绝对不能出现 SET t = NOW()、SET x = rand()、INSERT ... AUTO_INCREMENT 这类命令——不同副本重放会算出不同结果，状态机静默发散，而 Raft 层完全察觉不到（日志明明是一模一样的）。
正确做法：在 Leader 上先把非确定值算好，把结果写进日志。
这和 MySQL binlog 从 statement 格式改成 row 格式，是同一个原因、同一个教训。

真实系统两个都有，而且会打两次盘

TiKV 的一次写：

  客户端写
     ↓
  ① append 到 Raft log  ──→ 复制给另外 2 个副本
     ↓                        （它们也各自 append + 落盘）
     落盘（raftdb 的 WAL）
     ↓
  ② 过半确认 = committed，commitIndex 推进
     ↓
  ③ apply：写 RocksDB kvdb   ←── 这一层又有一个 WAL
     ↓
     lastApplied 推进，现在才读得到

一次写落两次盘，这是共识系统的固有成本。TiKV 为此专门做了 Raft Engine（替代 RocksDB 存 raft log）来省掉一层。另一条路是让两者合一：MySQL Group Replication、阿里 X-Paxos 让 binlog 兼任 Raft log。

那第二层版本是怎么对上的

§3.24 的第 3 步（lastApplied >= readIndex）解决的是「这台机器的状态机重放够不够新」。但一个事务型 KV 还要回答另一个正交的问题：「这次读该看哪个快照」。这是另一层：

TiKV / Percolator

key 存成 (key, ts) → value。事务从全局 TSO 拿一个 start_ts，读取 commit_ts <= start_ts 的最大版本。

Spanner

用 TrueTime 给的时间戳。read at timestamp t 会等到所有 t' <= t 的事务都完成（safe time）才返回。

MySQL InnoDB

ReadView + undo 版本链。原理同构，但时间戳是本地事务 id，不是全局的——所以它只能做单机快照。

于是一次 TiDB 的快照读，实际上要过两道版本关：

① Raft 层：  等 lastApplied >= readIndex        ← 这台机器的日志重放够不够新
② MVCC 层：  取 commit_ts <= start_ts 的版本    ← 这次读该看哪个快照
一个值得记住的对照

Raft 的 index 之于集群，相当于 LSN 之于单机；
MVCC 的 start_ts 之于快照读，相当于 ReadView 之于 InnoDB 快照读。
第二层就是 Part 4 要展开的东西——分布式事务不是把 2PC 抄一遍，而是把单机 MVCC 那套版本机制搬到全局去。

3.30 单个 Raft 组的吞吐天花板

既然写全部经过 Leader，单个 Raft 组的写吞吐就被一台机器卡死了。生产上怎么办？

1
Multi-Raft / 分片 —— 唯一真正解决问题的手段
把 key space 切成成千上万个 Region/Shard，每个 Region 一个独立的 Raft 组，Leader 打散到全集群的机器上。单组不扩展，但组数可以无限扩展。TiKV、CockroachDB、YugabyteDB 全是这个路子。
代价：跨 Region 的事务需要 2PC（Part 4），Region 的分裂/合并/调度本身成了一个复杂子系统（TiKV 的 PD）。
2
Batching + Pipelining
一次 AppendEntries 带几百条 entry；不等上一轮 ack 就发下一轮（nextIndex 乐观前移，失败再回退）。这两个优化通常能把吞吐拉高一个数量级，而且不改变任何安全性论证。
3
并行落盘
Leader 本地 fsync 和发给 follower 可以同时进行——论文并没有要求「先本地持久化再发出去」。等过半（含自己）落盘即可提交。这一步能砍掉一个完整的磁盘延迟。
4
Follower / Lease Read 卸载读
只对读有用，而且如 §3.27 所说，省的是带宽和 CPU 不是 RTT。
顺手纠正一个常见误解

「节点从 3 加到 7，写会变慢」——延迟未必。提交只需要过半 ack，7 节点等的是第 4 快的那个节点，3 节点等的是第 2 快的。多了候选者，反而更容易避开某个临时抽风的慢节点（这叫 hedging 效应）。
真正变差的是 Leader 的出向带宽（O(N)）和网络总流量。所以生产上用 3 或 5、极少到 7，理由是带宽与收益递减，不是延迟。
而节点数必须是奇数的理由你在 Part 0 就答对了：4 节点的过半是 3，容错能力和 3 节点（过半 2）一样都是 1，多花一台机器买不到任何东西。

一个 Raft 组就一定线性一致吗？

不一定。Raft 给你的是线性一致的日志，系统要线性一致还差两件事（论文 §8）：

  • 写要去重：Leader 提交了你的写但回复丢了，客户端重试 ⇒ 同一命令进日志两次、执行两次。需要客户端带唯一 ID + 序号，状态机记录每个客户端最后执行的序号。
  • 读要走 ReadIndex / Lease Read：本地读不线性一致。

少任何一个，底下是 Raft 也不是线性一致。

等 apply 的过程中 lease 过期了、Leader 下台了，这次读还算数吗？

算数。线性一致点是「确认成功的那一刻」，不是「真正读数据的那一刻」。

ReadIndex：读请求到达后，Leader 发了一轮心跳收到过半响应——那一刻它确实是 Leader，readIndex 覆盖了此前所有已确认的写。readIndex 以内的条目已提交、永不回滚，之后它下台改变不了这些内容。等本地 apply 到 readIndex 再读，返回的就是那一刻的状态，而那一刻落在这次读的「发起—返回」区间内。Lease Read 同理：只要求接纳这次读时 lease 有效。

Follower Read：Leader 把 readIndex 交给 follower 后死了也没关系。follower 可能还没收到那些条目，但新 Leader 按 Leader 完整性一定有，会发过来。

确认还没完成就出事，这次读作废。etcd 早期这种读会挂到超时（issue #9566），现在有 ErrLeaderChanged（etcdserver: leader changed）让它尽快失败。等 apply 也有上限：ErrTimeoutWaitAppliedIndex。

生产环境里 Raft 组的节点怎么放？延迟和吞吐大概多少？
放法典型配置写延迟主要看什么

两地三中心扛得住异地机房挂，扛不住主城市整体挂：主城市两个 AZ 同时没了只剩 1/5，凑不齐过半，TiDB 文档明确说会暂时不可用。

公开数字：etcd 文档里同机房 RTT「几百微秒」、美国境内约 50ms、跨洲可达 400ms；SSD fsync 通常 < 1ms。etcd 官方 benchmark（3 × 8 vCPU / 16GB / SSD）：单客户端写 583 QPS / 1.6ms，1000 客户端写 44,341 QPS / 22ms——单组写吞吐大约是「几万 QPS」量级，再往上靠 Multi-Raft。超时参数：etcd 默认心跳 100ms、选举 1000ms，建议心跳 ≈ 0.5–1.5 倍 RTT、选举 ≥ 10 倍 RTT；TiKV 默认 tick 1s、心跳 2 tick、选举 10 tick——一台机器上成千上万个 Raft 组，超时短了会互相踩。etcd 硬件指南建议成员尽量放在一个数据中心里。

AppendEntries 里 entries 从中间开始和 follower 不一样，直接覆盖吗？

Figure 2 接收方规则 3、4：已有条目和新条目冲突（同 index 不同 term）⇒ 删掉这条及之后所有；追加日志里还没有的新条目。逐条比：同 index 同 term 跳过，同 index 不同 term 从这里截断，不存在就追加。从中间开始不一样就覆盖——对，而且安全：prev 匹配 ⇒ 之前全部相同；冲突的那些必然未提交。

容易漏的是那个「如果」：没有冲突时，绝不能截断。你的日志比这次 RPC 覆盖的范围长时，后面多出来的必须保留。网络会乱序：一个旧的、较短的 RPC 晚到了，如果无条件「截到 prevLogIndex 再追加」，就会删掉你已经告诉 Leader「我有了」的条目——Leader 可能已经靠你这一票提交了它们。

同理，更新 commitIndex 的上限是这次 RPC 里最后一条新条目（etcd：commitTo(min(committed, lastnewi))，lastnewi = prev.index + len(entries)），而不是自己的最后一条——后者可能是还没被验证过的旧条目。

Batch 到底攒多少条才发？会不会拖慢写的响应？

不是「攒够 N 条再发」，是自然批量：上一轮发送/落盘还在进行时到达的请求，下一轮一起带走。低负载时每轮 1 条，不增加延迟；高负载时每轮变慢、攒得更多，批量自动变大。fsync 同理（group commit）。etcd 文档：etcd batches multiple requests together and submits them to Raft。

限制的是上限：etcd 服务端单条消息 1MB、流水线窗口 512 条；TiKV 是 1MiB / 256。

「故意等一等凑批」的参数也有，但默认关着——比如 MySQL 的 binlog_group_commit_sync_delay，默认 0 微秒。等得越久批越大、吞吐越高、单次延迟越长：etcd benchmark 从单客户端到 1000 客户端，吞吐高了 76 倍，平均延迟也从 1.6ms 涨到 22ms。

被移除的是 Leader：它 append 配置之后还接受写吗？

按论文：继续接受。C_new 提交前它照常处理写、复制日志，只是算过半时不算自己；提交后下台。etcd raft 对应 stepDownOnRemoval 选项。

生产上一般先做 Leader 转移，再移除旧节点（etcdctl move-leader）。转移期间确实会短暂停写：etcd raft 丢弃转移期间的新 proposal，让目标节点追平日志；太久会报 ErrTimeoutLeaderTransfer。

Raft 能解决并发写的数据竞争吗？

不能。线性一致是单个操作的性质。「读出来加一再写回去」是两个操作，并发执行时在完美线性一致的存储上照样丢更新——Part 4-A 矩阵里「丢失更新」那一行不在乎你底下是 InnoDB 还是 Raft。

Raft 解决「副本对顺序达成一致」；并发控制要在状态机里做：

  • 读-改-写做成一条命令：INCR x 作为一个日志条目，apply 时原子执行；
  • 条件写 / CAS：etcd 的 Txn（If(mod_revision(key) == 42) Then(Put) Else(…)），整个事务是一条日志，apply 时原子判断——本质就是快照隔离的 first-committer-wins；
  • 锁/租约 + fencing token（Part 6）；跨 Raft 组的多 key 事务 → Percolator / 2PC（Part 4-C）。

线性一致 ≠ 可串行化——又是 §3.27 那两条轴。Raft 给你前者，后者要自己搭。

member add 发给谁？新节点的初始配置从哪来？它刚启动时认为过半是几？

发给任意成员都行：follower 收到的 proposal 会转发给 Leader（etcd raft 默认开启），由 Leader 写进日志。

新节点的参数就是 member add 打印出来的：--initial-cluster = 当时的成员 ∪ 自己、--initial-cluster-state=existing。它启动时去 peer 那里拉集群当前成员，和自己的参数比对，对不上直接拒绝（member count is unequal）。

它刚启动时对配置一无所知：etcd 启动加入者的 Raft 时不带任何初始成员（existing 路径传的是 nil，走 raft.RestartNode），它不认为自己是投票成员，不会发起选举，也不存在「它认为过半是几」。配置随 Leader 发来的快照/日志一起到达。

两道保护：加完之后已启动的成员必须还能凑齐过半，否则拒绝（ErrNotEnoughStartedMembers，唯一特许的是 1→2）；先 member add --learner、追平后 member promote，没追平会被拒（ErrLearnerNotReady）。

3.32 自测题

先自己想 30 秒再展开。

1. Raft 的四个 index 分别是什么？哪些会被回滚？

lastLogIndex（已 append）、matchIndex[i]（Leader 记的各 follower 复制进度）、commitIndex（已提交）、lastApplied（已执行）。恒有 lastLogIndex >= commitIndex >= lastApplied。

只有 lastLogIndex 对应的那段尾巴会被回滚——未提交的日志随时可能被新 Leader 截断覆盖。commitIndex 以下的部分按定义永不回滚。matchIndex 是 Leader 的易失记账，新 Leader 上任会重置为 0 重新试探（3-B 的冲突回退）。

2. 为什么 ReadIndex 必须有第三步？只做前两步会发生什么？

前两步只保证「readIndex 这个数字是对的」——我确实还是 Leader，提交点确实是 7。但状态机是异步 apply 的，此刻 lastApplied 可能才 5。

直接读状态机就会拿到 index=5 时刻的值，丢掉了 6、7 两条已提交的写。客户端刚收到「写入成功」，转头读到旧值，线性一致性破裂。
第三步 等 lastApplied >= readIndex 做的事情，就是把日志的版本和状态机的版本对齐。

3. 新 Leader 为什么必须先提交一条 no-op？（至少说出两个理由）

理由一（读的正确性）：受 Figure 8 限制，新 Leader 不能直接提交旧任期的条目。它日志里那段「已复制到过半但没标记提交」的旧条目会一直悬着，commitIndex 停在偏小的位置。此时 readIndex := commitIndex 拿到的是过时的目标 ⇒ ReadIndex 前两步完美通过，照样读到旧值。no-op 是当前任期的条目，可以直接提交，一提交就把前面的旧条目顺带提交了（提交是前缀性的）。

理由二（成员变更的前提）：单节点成员变更有个 2015 年才发现的坑——新 Leader 必须先提交一条自己任期的日志，才能安全地发起新的成员变更，否则可能基于一个后来被回滚的配置做决策。

理由三（顺带的好处）：复制 no-op 的过程顺便完成了所有 follower 的 nextIndex 回退试探。

4. 「Dynamo 的 quorum 写」和「Raft 的日志 append」，具体差在哪？

表面都是「等过半确认」，含义完全不同：

Dynamo 的 W：把值发给 N 个副本，等 W 个回 ok。这 W 个副本上的值可能互相不一致——两个客户端并发写，不同副本收到的顺序不同，各存各的。冲突甩给读端（向量时钟 / LWW / CRDT）。这是数量的保证。

Raft 的提交：Leader 在 index=5 放了一条 entry，等过半 follower 复制了这一条。过半节点的 index=5 一定是同一条 entry（日志匹配性质）。并发写在到达 Leader 时就被定了序，根本不会产生冲突。这是内容与位置的保证。
底层数学都是「两个过半集合必相交」，但一个用它保证「读能碰到最新值」，另一个用它保证「新 Leader 必持有全部已提交日志」。

5. Raft 里有「quorum 读」吗？ReadIndex 那轮心跳算不算？

没有。Raft 不需要读过半副本再比较版本——读 Leader 一个就够了，因为 Leader 按定义持有全部已提交日志（Leader 完整性）。

ReadIndex 那轮心跳形式上要收过半响应，但它拿回来的不是数据，是「我还是不是 Leader」这一个 bit。数据一个字节都不从 follower 传。
所以它和 Dynamo 的 R=3 在带宽上差着数量级，而且并发的读请求可以合并成一次心跳确认——这就是为什么 ReadIndex 对吞吐的影响远小于对单次延迟的影响。

6. Follower Read 省了什么？不省什么？

不省那一轮确认 RTT——follower 仍然要向 Leader 要一个 readIndex，一致性保证完全来自 Leader 的那次确认。follower 还得等自己 lastApplied >= readIndex。

省的是 Leader 的数据传输带宽和状态机读取 CPU。所以它对「读多写少 + 单次读结果大（范围扫描）」的负载收益明显，对「高频读小 key」几乎没用。
注意别和 etcd 的 --consistency=s 混——那个不走 readIndex，是明确放弃线性一致换延迟。

7. 成员配置存在哪？为什么「一收到就生效、不等提交」？

存在日志里，是一条特殊的日志条目，走普通的 AppendEntries 复制；内容是 id → 地址的映射，不只是 id 集合。

不等提交是因为会死循环：提交 C_new 要先知道「过半」是几个 → 「过半」取决于当前生效的配置 → 当前生效的配置取决于 C_new 提交了没有。
所以 Raft 论文选择立即采用。代价是这条配置可能被新 Leader 回滚，而单节点变更的交集性质（maj_old + maj_new > |C_old ∪ C_new|）保证回滚期间也不会出现两个 Leader。
但 etcd 的实现不一样：配置变更在旧配置下提交、apply 时才生效，同时规定一次只能有一个未提交的配置变更。两种做法都安全。

8. 给集群加一个节点，会触发重新选举吗？

默认不会。Leader 继续是 Leader，只是算「过半」时用的数从 2 变成 3。过半数变化 ≠ 需要重新选举——Leader 的合法性来自任期和选票，不来自集群规模。

两个例外：
① 被移除的是 Leader 自己——它在 C_new 提交后才退位，期间在管理一个不含自己的集群。
② 被移除的节点收不到心跳、超时、自增 term 发起选举——term 更高会把现任 Leader 打下来，它自己又不在配置里选不上。解法是 PreVote（先问一轮、不实际自增 term）和 CheckQuorum（刚收到过心跳的节点忽略投票请求）。
新节点不会这样捣乱：etcd 启动新成员时不带初始配置，它不会发起选举。新节点的问题是追日志期间可能拖住提交，所以要先当 learner。

9. 冷启动时，节点怎么知道集群里有谁、地址是什么？

这是个鸡生蛋问题（配置在日志里，复制日志要先有配置），Raft 的答案是：初始配置必须从外部给，不能从日志来。两条路：

静态引导：启动参数写死完整成员列表，如 etcd 的 --initial-cluster infra0=http://...,infra1=http://... 配 --initial-cluster-state new 和 --initial-cluster-token。地址就在这份列表里——Raft 自己不做服务发现，DNS SRV / K8s Service 只是帮你生成这份列表。

单节点引导：先起一台「只有我一个成员」的集群（自己就是过半，立刻当选），再逐个 member add。
关键细节：--initial-* 只在 data dir 为空的首次启动生效。集群跑起来后成员信息存进了 data dir，改配置文件不会改变集群成员。

10. 【综合】线上反馈「写接口返回成功了，立刻查却查不到」。用这一章的知识列出可能的原因。

按「从哪一层漏的」排查：

  1. 读走了本地读（最常见）。客户端读到的是某个节点直接返回的状态机内容，没走 ReadIndex。如果那个节点是僵尸 Leader 或落后的 follower，就会读到旧值。—— 查读请求用的是哪种一致性级别（etcd 的 serializable、TiDB 的 follower read 配置）。
  2. ReadIndex 少了第三步，或 apply 严重滞后。commitIndex 和 lastApplied 的窗口被撑大了：状态机执行慢（大事务、存储引擎写放大、compaction 抢 IO）。—— 查 apply 延迟指标和 raft 落后指标。
  3. 新 Leader 刚上任还没提交 no-op。窗口很短但真实存在，表现为「切主后几十毫秒内读到旧值」。—— 查读失败的时间点是否紧跟一次 leader 切换。
  4. 写其实没成功。客户端超时后重试，第一次的响应丢在路上——这是 Part 0 的「第三态」，返回的「成功」可能是某次重试的，而真正生效的顺序和你以为的不同。
  5. 读写路由到了不同的分片/集群。Multi-Raft 下 Region 发生了分裂或调度，客户端缓存的路由过期。

诊断的分水岭：先确认「写是否真的 committed」（查 raft 日志的 index 和 term），再确认「读走的是哪条路径」。前者是 Part 3-B 的问题，后者是这一章的问题——混在一起查会一直找不到。
