事务：你买的是三个假设，而第二个一直在打折

Part 0 开篇说过：单机编程送你三个免费假设，分布式把它们一个个收走。事务做的是反向的事——它向并发的世界卖给你三个假设，让你可以像世界是单线程的那样写代码。

A
「要么全做，要么全不做」
原子性。这条卖得很实在，基本不打折——靠 undo log 回滚。
I
「我看到的世界是静止的，只有我一个人在改」
隔离性。这一条一直在打折出售。「隔离级别」这四个字的全部含义，就是这条假设你要买几成。
而最贵的那一档（可串行化）太贵，于是几乎所有人用的都是打折版——包括你正在维护的那个系统。
D
「写下去就不会消失」
持久性。这条的地基是 fsync——正是 3-C 里 Raft 那条同样的地基。地基塌了，上面的证明一起塌。
这一章要让你能回答的一个问题

「我们用的是 MySQL 默认的可重复读，所以并发是安全的」——
这句话在你的团队里大概率有人说过。这一章结束时你会知道它错在哪，以及那个叫写偏斜的洞长什么样：RR 挡不住，快照隔离也挡不住，而且它不报错、不死锁、不留痕迹。

为什么分布式课程要回头补单机事务

因为分布式事务 = 跨分片的原子提交（2PC 家族） + 全局的版本与可见性（MVCC 的分布式版）。
第二项就是 3-D 结尾说的「第二层版本」——TiKV 的 start_ts、Spanner 的 TrueTime 时间戳，本质上都是把 InnoDB 的 ReadView 搬到全局去。
不把单机这层弄透，Percolator 那一章会变成背诵。

4.1 ACID：四个字母里只有两个半是真的

ACID 这个缩写来自 Härder 与 Reuter 1983 年的论文。它首先是个好记的词，其次才是个精确的定义——这一点值得知道，因为四个字母的严谨程度差别很大。

字母通常的说法实际情况
A 原子性
atomicity		要么全做，要么全不做 定义清晰。但注意它说的不是并发（那是 I），而是可中止性：出错时能把做了一半的东西撤回去。
Rich Hickey 说过，如果重新命名，这个字母应该叫 abortability。
C 一致性
凑数的		事务把数据库从一个一致状态带到另一个一致状态 这个字母是为了拼出 ACID 才加进来的。「一致」指的是你的应用定义的不变量（账户余额不为负、值班医生至少 1 人）。
数据库没有办法知道你的不变量是什么，所以它无法保证 C。能保证的只有外键、唯一约束、CHECK 这些你显式告诉它的部分。
C 是应用的责任，A、I、D 才是数据库的承诺。
I 隔离性
本章主线		并发事务互不干扰 教科书定义是「效果等同于串行执行」（可串行化）。
但因为太贵，现实里绝大多数数据库默认不提供它，而是提供一个打过折的版本。
「隔离级别」= 折扣力度。这一章 90% 的篇幅在这四个字母的第三个上。
D 持久性
durability		提交后数据不会丢 定义清晰，但地基脆弱。它最终落在 fsync 上，而 fsync 会被磁盘固件、虚拟化层、云盘缓存骗——
这正是 3-C 讲 Raft 持久化时的同一段话。单机和分布式在这一层是同一个问题。
ACID 的反面不是 BASE

BASE（Basically Available, Soft state, Eventually consistent）也是一个为了对仗而造出来的缩写，唯一确定的含义是「不是 ACID」。
真正有意义的问题从来不是「选 ACID 还是选 BASE」，而是：我需要哪些不变量、愿意为它们付多少延迟和吞吐。
Part 2 的 CAP 也是同一类词——好记，但用来做技术决策时几乎总是被误用。

单对象 vs 多对象

还有一个常被跳过的区分：

单对象写

「把这一行的这个字段改掉」。几乎所有存储引擎——包括 Redis、包括大多数 NoSQL——都提供单对象的原子性和隔离性。
这是免费的，因为一个对象天然就是一个锁的粒度。

多对象事务

「把 A 的余额减 100，同时把 B 的余额加 100」。这才是事务真正的难点，也是分布式系统里最贵的东西——因为 A 和 B 可能在不同的分片、不同的机房。
Part 4-B 的 2PC/TCC/Saga 全部在解决这一件事。

4.2 隔离级别：一个按「禁止什么」定义的烂摊子

ANSI SQL-92 定义隔离级别的方式是列举它禁止哪些异常：

级别脏读不可重复读幻读说明
READ UNCOMMITTED可能可能可能几乎无人使用
READ COMMITTED禁止可能可能PostgreSQL / Oracle / SQL Server 的默认
REPEATABLE READ禁止禁止可能MySQL InnoDB 的默认
SERIALIZABLE禁止禁止禁止效果等同于串行执行

这张表你大概背过。但它是个设计错误，1995 年 Berenson 等人的论文 A Critique of ANSI SQL Isolation Levels 就把它拆掉了。三个理由：

1
「禁止这三种异常」不等于「安全」。异常的清单是不完整的。丢失更新和写偏斜都不在 ANSI 的三种异常里，所以一个级别可以合法地宣称「我禁止了全部三种异常」，同时对它们完全不设防。这正是 RR 的处境。
2
异常本身的定义含糊。比如「幻读」的原始表述是基于锁的实现来描述的，换成 MVCC 实现之后完全对不上号。
3
各家实现的同名级别根本不是一回事。见下表——同一句 SET TRANSACTION ISOLATION LEVEL REPEATABLE READ，在三个数据库里是三种不同的东西。

REPEATABLE READMVCC 快照读 + Next-Key Lock。

把这条记住

隔离级别的名字不是规格说明，只是一个标签。你唯一能依赖的是「这个数据库的这个版本在这种并发模式下实际会发生什么」。
所以这一章接下来不再讲级别的名字，只讲异常——异常是可以复现、可以计数的，名字不是。

4.3 并发异常动物园

七种异常，按「谁读谁写」分成三类。后三种不在 ANSI 的清单里，而它们才是线上真正出事的那几种。

脏写 dirty write
写-写
覆盖了另一个尚未提交的事务写的值。后果：那个事务回滚时，把你的值也一起撤了。
几乎所有数据库在所有级别都禁止它——靠行级排他锁，持有到提交。这是唯一一个「白送」的。
脏读 dirty read
读-写
读到了另一个事务尚未提交的值。那个事务一旦回滚，你读到的是一个从未存在过的世界。
不可重复读 / 读偏斜
non-repeatable read
同一个事务里读两次同一行，值变了。更危险的形式叫读偏斜：分两次读 A 和 B 两个账户，中间有人从 A 转账到 B，于是你看到的总额凭空少了 100——两次读各自都是「已提交的值」，合起来却是一个从未存在过的状态。
幻读 phantom read
范围查询
同一个范围查询两次，行数变了（别人插入或删除了落在范围里的行）。和不可重复读的区别：那个是「同一行变了」，这个是「多了/少了行」。
锁能锁住已存在的行，锁不住「还不存在的行」——这就是需要间隙锁的原因。
丢失更新 lost update
不在 ANSI 清单里
读-改-写循环：两个事务都读到 100，都算出 110，都写回去 ⇒ 只加了一次。
经典场景：计数器、库存扣减、把 JSON 读出来改一个字段再写回去。
MySQL RR 挡不住这个模式（但如果你写成 UPDATE x = x + 10，那是「当前读」，就能挡住——取决于你怎么写 SQL，不取决于隔离级别）。
写偏斜 write skew
本章主角
两个事务读同一批数据做决策，然后各自写不同的行。因为写的行不冲突，没有任何锁会撞上；因为读的是快照，没有任何版本检查会失败。
RR 挡不住，快照隔离挡不住，Oracle 的 SERIALIZABLE 也挡不住。而且不报错、不死锁、不留痕迹。§4.6 详述。
写偏斜的「插入」变体
phantom write skew
同样是「读一批数据做决策」，但决策的结果是插入一行新的：两个人同时查「这个会议室 10 点有人订吗」，都查到没有，都插入了预订。
比普通写偏斜更难防——连要加锁的那一行都还不存在。解法是物化冲突或范围锁。

4.4 MVCC 与 ReadView：InnoDB 的快照是怎么做出来的

先纠一个极常见的混淆：版本信息在 undo log，不在 redo log

redo log 是物理/物理逻辑日志：「把表空间 5 第 137 页 offset 92 处的 4 个字节改成 0x2A」。它只用于崩溃恢复时的 roll-forward，和可见性判断毫无关系。
undo log 才是 MVCC 的载体：它保存每一行的历史版本，既用于回滚，也用于快照读。
搞混的代价：会想不通「redo log 都刷盘了，事务怎么还能回滚」。

行上的两个隐藏列

InnoDB 的每一行除了你定义的字段，还偷偷带着：

| id | name  | balance | DB_TRX_ID | DB_ROLL_PTR |
                            ↑             ↑
              最后修改这行的事务 id   指向 undo log 里的上一个版本

顺着 DB_ROLL_PTR 一路回溯，就得到这一行的版本链，从新到旧：

[trx=30 balance=300] → [trx=22 balance=200] → [trx=15 balance=100] → ...
    最新已提交              undo log 里            更早的 undo

ReadView：决定我该看链上的哪一节

快照读的那一刻，InnoDB 生成一个 ReadView，四个字段：

m_ids
[..]
创建这个 ReadView 时仍然活跃（未提交）的事务 id 集合
min_trx_id
min(m_ids)
活跃集合里最小的 id
max_trx_id
next id
下一个将要分配的事务 id（不是 max(m_ids)）
creator_trx_id
我自己
当前事务的 id

然后沿版本链从新往旧走，对每个版本的 DB_TRX_ID 做四步判定，第一个可见的就是答案：

trx == creator_trx_id        → 可见（我自己改的，当然看得见）
trx <  min_trx_id            → 可见（在我建 ReadView 之前就已提交）
trx >= max_trx_id            → 不可见（在我之后才开始的事务）
trx 在 m_ids 里              → 不可见（我建 ReadView 时它还没提交）
否则                          → 可见
RC 和 RR 的实现差异只有一行

RC：每条语句都新建一个 ReadView。所以别人刚提交的，你下一条语句就看得见 ⇒ 不可重复读。
RR：整个事务只在第一次快照读时建一个 ReadView，之后一直复用。所以事务期间世界是静止的 ⇒ 可重复读。
就这一个区别。两个级别共用同一套版本链、同一套判定算法。

4.5 当前读与 Next-Key Lock：MVCC 管不到的那一半

MVCC 只服务快照读。下面这些是当前读——它们读的是最新版本，绕过版本链：

SELECT ... FOR UPDATE          -- 排他
SELECT ... LOCK IN SHARE MODE  -- 共享（8.0 起写作 FOR SHARE）
UPDATE ...
DELETE ...
INSERT ...                       -- 隐含一次唯一性检查，也是当前读

为什么必须读最新版本？因为要改的东西必须是当下真实存在的那一份——你不能基于半分钟前的快照去扣库存。

于是 MVCC 在这里帮不上忙，InnoDB 换成锁：

Record Lock

锁住索引上的一条记录。注意是索引，不是行——没走索引就会退化成锁全表。

Gap Lock 间隙锁

锁住两条记录之间的空隙，不让别人往缝里插。
它锁的是「还不存在的行」——这是防幻读的关键。

Next-Key Lock

Record Lock + 它前面的 Gap Lock，即左开右闭区间 (a, b]。
InnoDB 在 RR 下的默认加锁单位。

所以「InnoDB 的 RR 能防幻读」是两套机制拼出来的

快照读：靠整个事务复用同一个 ReadView ⇒ 新插入的行 DB_TRX_ID 落在 m_ids 或 >= max_trx_id ⇒ 不可见。
当前读：靠 Next-Key Lock 锁住范围 ⇒ 别人根本插不进来。
缺任何一套都防不住。而 ANSI 标准里的 RR 根本不要求防幻读——InnoDB 是超额交付。

间隙锁的账单
  • 并发下降：一条 SELECT * FROM t WHERE age > 18 FOR UPDATE 可能锁住一大片区间，所有落在区间内的插入全部排队。
  • 死锁变多：间隙锁之间可以共存（都是 S 型间隙），但插入意向锁会和它冲突 ⇒ 两个事务各持一段间隙、各自想插对方的间隙 ⇒ 死锁。这是线上最常见的 InnoDB 死锁形态。
  • 没走索引就是灾难：条件列上没有索引时，InnoDB 会对扫过的每一行加 Next-Key Lock，实际效果接近锁表。「我只更新了一行，为什么把整个表锁住了」——十有八九是这个。

顺带：RC 级别下 InnoDB 不加间隙锁（只加 record lock），而且对 UPDATE/DELETE，WHERE 求值之后会释放不匹配行上的锁——所以 RC 的并发通常明显好于 RR，代价是它防不住幻读。很多高并发系统特意把 MySQL 调成 RC，就是为了这个。

锁的是「扫过的行」，不是「匹配的行」

这一条最反直觉，官方文档原话："A locking read, an UPDATE, or a DELETE generally set record locks on every index record that is scanned in the processing of an SQL statement. It does not matter whether there are WHERE conditions in the statement that would exclude the row." 以及："If you have no indexes suitable for your statement ... every row of the table becomes locked, which in turn blocks all inserts."
所以 §4.6 值班表那条 SELECT count(*) … WHERE on_call = true FOR UPDATE：on_call 没索引 ⇒ 全表扫 ⇒ 锁全表；有索引 ⇒ 锁那段索引范围。可 on_call 是布尔列、选择性极差，优化器很可能不走索引——结果还是锁全表。
本章的迷你引擎为了简单，FOR UPDATE 只锁匹配的行——结论方向（加锁能挡住写偏斜）不变，但它低估了真实代价。

4.6 快照隔离与写偏斜

先把快照隔离（SI）说清楚

规则一
事务开始时拿一个一致性快照，整个事务的读都从这个快照来（= RR 的 ReadView）
规则二
first-committer-wins：两个事务写了同一行，先提交的赢，后提交的被中止

MySQL 的 RR 只有规则一，没有规则二——它靠行锁把并发写串起来而不是中止掉。所以严格说 MySQL RR 不是快照隔离，它是「快照读 + 2PL 写」的混合体。
PostgreSQL 的 REPEATABLE READ 才是真正的 SI，冲突时会抛 ERROR: could not serialize access due to concurrent update，逼你重试。

写偏斜：SI 和 RR 共同的盲区

经典场景：医院值班表，业务不变量是「任何时刻至少有 1 个医生在岗」。现在 Alice 和 Bob 都在岗，两人同时想请假。

T1 (Alice)                              T2 (Bob)
──────────────────────────────────────────────────────────────────
BEGIN                                   BEGIN
SELECT count(*) FROM doctors
  WHERE on_call = true
  → 2  ✓ 满足「>= 2，我可以走」
                                        SELECT count(*) FROM doctors
                                          WHERE on_call = true
                                          → 2  ✓ 满足「>= 2，我可以走」
UPDATE doctors SET on_call = false
  WHERE name = 'Alice'
                                        UPDATE doctors SET on_call = false
                                          WHERE name = 'Bob'
COMMIT                                  COMMIT
──────────────────────────────────────────────────────────────────
结果：0 个医生在岗。不变量被破坏，而且没有任何报错。

为什么所有防线都失效：

防线拦住了吗为什么
行锁 / 脏写保护没有T1 改的是 Alice 那行，T2 改的是 Bob 那行。两把锁根本不在同一个东西上。
Next-Key Lock没有两个 SELECT 都是普通快照读，压根没加锁。
SI 的 first-committer-wins没有它只检测写-写冲突。这里两个事务写的是不同的行，没有写-写冲突。
Oracle 的 SERIALIZABLE没有它实际实现的是 SI，同上。名字骗了你。
PostgreSQL 的 SERIALIZABLE（SSI）拦住SSI 会跟踪读-写依赖：它发现 T1 读的集合被 T2 的写改变了、反之亦然，构成了危险的依赖环 ⇒ 中止其中一个。
显式 SELECT ... FOR UPDATE拦住把「读」这个动作物化成一把锁。T2 的 SELECT 会阻塞，等 T1 提交后重新读到 count=1 ⇒ 它的检查失败，自己放弃。
代价见 §4.5：InnoDB 锁的是扫过的行，这条语句很可能锁全表。更好的做法是锁一个小的代理对象——比如先 SELECT … FROM shifts WHERE id = ? FOR UPDATE 锁住这一班次的那一行，所有想改这班值班的事务都在这一行上排队。
写偏斜的通用形状

凡是符合下面这个模式的代码，都要怀疑写偏斜：

BEGIN
  SELECT ... ;                  -- ① 读一批数据，检查某个条件
  if (条件满足) {                -- ② 基于读到的结果做决策
      UPDATE / INSERT / DELETE;  -- ③ 写入，而写的对象可能不是 ① 读的那些行
  }
COMMIT

① 读到的东西是你决策的前提，而这个前提在 ③ 执行时可能已经被别人推翻了。
数据库看不见你脑子里的那个 if，它只看见读和写——所以它不知道这两者之间有因果关系。
真实例子：抢会议室、抢座位、库存扣减、唯一用户名检查、账户余额不能为负、值班表、双花。

4.7 可串行化的三条路

如果打折版太危险，为什么不都买全价的？因为全价的三种实现各有各的贵法。

1
实际串行执行 —— 干脆别并发
单线程按顺序跑完每个事务。可串行化的定义是「等价于某个串行顺序」，那最省事的实现就是真的串行。
能用的前提：① 整个工作集放得进内存 ② 事务必须短（不能有交互式等待）③ 通常要求事务以存储过程形式提交，一次性发过去，不能来回聊天。
代表：Redis（单线程）、VoltDB / H-Store、Datomic。
吞吐天花板 = 单核。想扩展只能分区，而跨分区事务会把优势全吃掉——这个矛盾会在 Part 4-C 的 Calvin 里再次出现。
2
两阶段锁 2PL —— 悲观派，五十年的老办法
读加共享锁、写加排他锁；只增不减地获取（growing），到提交时一次性全放（shrinking）——这就是「两阶段」的意思。
注意：2PL 和 2PC 完全是两回事。2PL 是单机并发控制，2PC 是跨节点原子提交。它们唯一的共同点是名字里都有个「两阶段」。这是这门课里最容易混的一对术语。
代价：① 锁等待导致延迟长尾极难看 ② 死锁需要检测和中止 ③ 范围查询要间隙锁，并发进一步下降。
代表：MySQL SERIALIZABLE、SQL Server 默认、传统商业数据库。
3
可串行化快照隔离 SSI —— 乐观派，2008 年才出现
先按 SI 跑（读快照，不加读锁，全速前进），提交时才检查：我读到的前提，有没有被别人推翻？被推翻就中止重试。
具体检测两种危险模式：① 读到了一个陈旧的 MVCC 版本（我读之后，那个事务提交了）② 我读过的东西被别的事务改了。构成危险依赖环就中止。
代价：低冲突时几乎白送，高冲突时中止率飙升——每一次中止都意味着整个事务白做一遍，而白做的功照样烧 CPU。而且需要应用层有正确的重试逻辑。
代表：PostgreSQL SERIALIZABLE、CockroachDB、FoundationDB。
4
实验 4 · 2PL vs SSI：两种并发控制，两张不同的账单
一个付「等待」，一个付「白做的功」——把热点集中度拉满，看哪张账单涨得快
2PL（悲观：等锁 / 死锁中止）
SSI（乐观：全速跑 / 提交时检查）

那实践中该怎么办

一个可操作的决策顺序
  1. 先问：我有哪些业务不变量？写下来。没写下来的不变量，数据库一定保护不了。
  2. 能用数据库约束的，就用约束。唯一索引、外键、CHECK——它们是数据库知道的不变量，因此能真正保护。「抢唯一用户名」这类写偏斜，一个唯一索引就解决了，比任何隔离级别都可靠。
  3. 剩下的，把读物化成锁。SELECT ... FOR UPDATE 锁住你决策所依赖的那些行。这是最通用、最容易审查的办法。
  4. 锁不到的（要插入的行还不存在），物化冲突。造一张「会议室-时间段」的占位表，把不存在的冲突变成一行真实的行，然后锁它。丑，但有效。
  5. 实在复杂的，上 SSI 并写好重试。前提是你的应用能正确重试——重试逻辑写错比不用 SSI 更危险。

不要做的事：把隔离级别从 RC 调到 RR 然后认为问题解决了。实验 1 的矩阵已经告诉你它对写偏斜毫无作用。

4.8 这一切到了分布式会怎样

单机事务的每一个部件，在分布式里都会遇到一个对应的、更难的问题。这张表是 Part 4-B / 4-C 的地图：

单机分布式对应物新增的难点
原子提交
（一个引擎说了算）		2PC / TCC / Saga
Part 4-B		 没有一个「说了算」的人。协调者宕机 ⇒ 参与者永远等下去（3-A 演示过的阻塞）。
解法：把协调者本身做成一个 Raft 组。
事务 id 递增
（一个计数器）		全局时间戳 TSO / TrueTime
Part 4-C		 「谁在前谁在后」变成了 Part 1 的问题。TiDB 用中心化 TSO（单点、但够快），Spanner 用 TrueTime + commit wait（把不确定性等掉）。

（内存里的一张表）		分布式锁 / Percolator 的 primary lock 锁的持有者可能在另一台机器上、可能已经死了。需要租约、fencing token、清理协议。

（一张等待图）		分布式死锁检测 / 超时 等待图散在多台机器上，构建它本身就是个分布式问题。大多数系统干脆放弃检测，改用超时。
写偏斜写偏斜，但更容易发生 跨分片的读没有天然的一致快照，前提被推翻的窗口更大。这个洞不会因为换成分布式数据库就自动补上。
一句话的承上启下

Part 3 解决的是「同一份数据的多个副本保持一致」，Part 4 解决的是「一个事务跨多份不同的数据要么全做要么全不做」。
这是两个正交的问题，真实系统需要两个都解决——TiKV 的做法就是：每个分片内部用 Raft 复制（Part 3），跨分片用 Percolator 式 2PC（Part 4）。
而 2PC 之所以在那里不再阻塞，正是因为它的协调者状态被 Raft 复制了——3-A 埋的那个伏笔，在 Part 4-C 兑现。

4.9 自测题

先自己想 30 秒再展开。

1. ACID 里哪个字母是数据库无法保证的？为什么？

C（一致性）。它指的是「你的应用定义的不变量」——账户余额不为负、值班医生至少 1 人、订单总额等于明细之和。

数据库无法知道你的不变量是什么，因此无法保证它。它只能保护你显式告诉它的那部分：唯一索引、外键、CHECK 约束。
A、I、D 是数据库的承诺，C 是应用的责任。这个字母当初是为了拼出 ACID 才加进去的。

2. MVCC 的版本链存在哪里？（这题有个极常见的错误答案）

undo log，配合行上的两个隐藏列 DB_TRX_ID（最后修改这行的事务 id）和 DB_ROLL_PTR（指向上一个版本）。

常见错误答案是 redo log。redo log 是物理/物理逻辑日志（「第 137 页 offset 92 改成 0x2A」），只用于崩溃恢复的 roll-forward，和可见性判断毫无关系。
搞混的代价：会想不通「redo log 都刷盘了，事务怎么还能回滚」——因为回滚靠的是 undo，不是 redo。

3. RC 和 RR 在 InnoDB 里的实现差异是什么？

ReadView 什么时候创建。

RC：每条语句都新建一个 ReadView ⇒ 别人刚提交的你下一句就看得见 ⇒ 不可重复读。
RR：整个事务只在第一次快照读时建一个，之后复用 ⇒ 事务期间世界静止 ⇒ 可重复读。
两者共用同一套版本链和同一套可见性判定算法。另外 RC 不加间隙锁，这是它并发更好的原因。

4. InnoDB 的 RR 能防幻读吗？靠什么？

能，但靠的是两套独立机制——只说一套是不完整的：

快照读（普通 SELECT）：整个事务复用同一个 ReadView，新插入的行 DB_TRX_ID 落在 m_ids 里或 >= max_trx_id ⇒ 不可见。

当前读（SELECT ... FOR UPDATE / UPDATE / DELETE）：读最新版本，MVCC 帮不上忙 ⇒ 靠 Next-Key Lock（记录锁 + 间隙锁）锁住范围，别人插不进来。
补充：ANSI 标准的 RR 允许幻读——InnoDB 是超额交付，别把「InnoDB 的 RR」和「标准的 RR」当成一回事。

5. 什么是写偏斜？为什么 RR 和快照隔离都挡不住？

两个事务读同一批数据做决策，然后各自写不同的行。例如两个医生同时检查「在岗人数 >= 2」，都通过，然后各自把自己设为不在岗 ⇒ 0 人在岗。

所有防线都失效的原因是同一个：它们写的不是同一行。
· 行锁不冲突（改的是不同行）
· Next-Key Lock 不生效（那两个 SELECT 是快照读，压根没加锁）
· SI 的 first-committer-wins 只检测写-写冲突，这里没有
根因：读到的结果是决策的前提，而数据库看不见你代码里那个 if——它不知道读和写之间有因果关系。

6. 2PL 和 2PC 有什么关系？

没有关系。唯一的共同点是名字里都有「两阶段」。

2PL（两阶段锁）：单机并发控制。两个阶段是「只获取锁」和「只释放锁」，用来实现可串行化。
2PC（两阶段提交）：跨节点的原子提交协议。两个阶段是 prepare 和 commit，用来保证多个参与者要么全做要么全不做。
这是这门课里最容易混的一对术语，面试里也常拿来筛人。

7. Oracle 的 SERIALIZABLE 真的可串行化吗？

不是。Oracle 的 SERIALIZABLE 实际实现的是快照隔离，因此写偏斜照样会发生。

这是数据库史上最著名的命名陷阱之一，也是 1995 年 Berenson 那篇批评论文的动机之一。
更一般的教训：隔离级别的名字不是规格说明，只是一个标签。同一个 REPEATABLE READ 在 MySQL 是「快照读 + 2PL 写」，在 PostgreSQL 是真正的 SI（带 first-committer-wins，会抛序列化错误）。
你唯一能依赖的是：这个数据库的这个版本在这种并发模式下实际会发生什么。

8. 2PL 和 SSI 各自在什么场景下更好？

它们付的是两种不同的账单。
2PL 的账单是等待：被挡住的事务停在那里，线程闲置、延迟长尾难看；但已经做过的功不会浪费，等到了就接着做，行为可预测。
SSI 的账单是白做的功：谁也不等，读事务完全无锁；但验证不通过就整个事务从头再来，而白做的那部分照样烧 CPU。

低冲突、事务短 → SSI 更合适（中止率接近 0，延迟分布好看得多）。
高冲突、事务长 → 2PL 更稳（SSI 的白做比例会涨到有效功的几倍，而且中止是随机打击，尾延迟同样会炸）。
注意墙上时间未必差很多——差的是 CPU。而那些 CPU 要从这台机器上别的事情里扣。

还有一个常被忽略的前提：SSI 要求应用层有正确的重试逻辑。重试逻辑写错（比如重试时复用了上次读到的值）比不用 SSI 还危险。
实验 4 里把热点集中度从 0 拉到 100%，看 SSI 那根「白做的操作」柱子怎么涨——那才是它真正的账单。

9. 「抢唯一用户名」这类写偏斜，最好的解法是什么？

唯一索引。不是隔离级别，不是锁，是约束。

原因回到第 1 题：数据库只能保护它「知道」的不变量。唯一索引把「用户名不能重复」这个业务规则告诉了数据库，于是它能在任何隔离级别下可靠地保护它。
而如果你写成「先 SELECT 查一下有没有，没有就 INSERT」，那就是一个标准的写偏斜插入变体——连要加锁的那一行都还不存在，任何隔离级别都救不了你。
通用原则：能变成约束的不变量，一律变成约束。

10. 【综合】库存扣减接口在大促时偶尔超卖。用这一章的知识列出可能的原因和修法。

先定位是哪一类：

  1. 丢失更新——代码写成了「读-改-写」：SELECT stock → 应用里算 stock-1 → UPDATE SET stock = 99。两个请求都读到 100，都写 99 ⇒ 卖了两件只扣了一件。
    修法：改成原子的当前读写 UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock >= 1，然后检查影响行数。这一条改完通常就好了。
  2. 写偏斜——代码是「先查够不够，够就插一条订单」。查和插作用在不同的表上，锁不会撞。
    修法：SELECT ... FOR UPDATE 锁住库存行，把读物化成锁；或者给库存加 CHECK (stock >= 0) 让数据库兜底。
  3. 隔离级别被调成了 RC——为了并发把 MySQL 调成 RC 是常见操作，但 RC 不加间隙锁，范围条件的保护更弱。
  4. 根本没在一个事务里——扣库存和建订单分成了两个事务，或者跨了两个服务。这已经是 Part 4-B 的问题了。

排查顺序：先看 SQL 是不是「读-改-写」（最常见，也最好改），再看有没有跨表/跨服务的决策依赖，最后才怀疑隔离级别。
反过来说：如果有人一上来就说「把隔离级别调高就行了」，那大概率没找到真正的原因——实验 1 的矩阵告诉你 RR 对写偏斜毫无作用。
