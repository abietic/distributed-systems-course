Part 2 · Replication & Consistency

"一致性"这个词，得先拆成七八个才能用

这一章从一个常见问题开始：PostgreSQL 的 ON CONFLICT 到底对应哪一种一致性语义？把它答清楚，需要用到这一章几乎全部的概念。

-- 同一条 SQL 的三种写法，三种完全不同的一致性语义
INSERT INTO counters(...) VALUES (...)
ON CONFLICT (counter_key) DO NOTHING;                            -- ① first-write-wins

ON CONFLICT (counter_key) DO UPDATE SET val = EXCLUDED.val;      -- ② last-arriving-wins

ON CONFLICT (counter_key) DO UPDATE
  SET cnt = counters.cnt + EXCLUDED.cnt;                         -- ③ 这其实是一个 CRDT
写法真实语义会丢并发更新吗
DO NOTHINGfirst-write-wins
不是 LWW		不会。幂等插入，重试安全 —— 这正是 Lab 0 里那张去重表的 SQL 版本。
DO UPDATE SET c = EXCLUDED.clast-arriving-wins会丢。整行覆盖：先到那次改的字段被后到的整行抹掉。经典的 lost update。
SET c = t.c + EXCLUDED.c基于当前值合并不会。这就是一个 G-Counter，本章 §2.6 的主角。
DO UPDATE ... WHERE t.version < EXCLUDED.version条件写 / 乐观锁不会。冲突方失败并重试，把决定权交回应用。
到达顺序的 "last" 为什么更安全

第二行的 "last" 是到达数据库的顺序，不是时间戳大小。顺序来自数据库的行锁与 MVCC —— 一个单一的、真实存在的串行化点，完全不受任何机器时钟影响。
这等于把 Part 1 §1.5 检查表的第三条做到极致：干脆不用时间戳。所以 Part 1 里那个"时钟歪了丢错人"的事故，在这条路径上不会发生。
但 lost update 仍然会发生 —— 只是丢法从"丢错人"变成了"后到的整行盖住先到的"。§2.6 会给你一张判断该用哪种写法的表。

2.1 复制的三种拓扑

所有复制方案都是这三种之一，或它们的组合。选哪种，决定了你会遇到哪一类问题。

单主 leader-based

所有写走同一个主库，从库只读。
MySQL 主从、PostgreSQL 流复制、Kafka 分区、MongoDB 副本集。

好处：写入天然串行化，不存在写冲突。
代价：主库是写入瓶颈和单点；主库故障要选主（Part 3）；从库有复制延迟（§2.2）。

多主 multi-leader

多个节点都能接受写，互相同步。
跨机房双写、CouchDB、离线优先 App。

好处：就近写入，机房级容灾。
代价：必然产生写冲突，必须有冲突检测（向量时钟）和解决策略（CRDT / siblings）。这是 Part 1 §1.5 那个坑的主场。

无主 leaderless

客户端直接并行写多个副本，靠 Quorum 保证正确。
Dynamo、Cassandra、Riak。

好处：没有选主，节点故障对可用性影响最小。
代价：一致性由 W/R 参数决定，需要读修复和反熵；同样会产生并发写冲突。

一句话选型

如果你能接受单点写入，永远优先选单主——它把冲突问题从"必须解决"降级为"不存在"。多主和无主的全部复杂度，都来自"允许并发写"这一个选择。
例如，让 counters 只由一个写入服务更新，本质上就是在做单写者——这是同一个思路的应用层版本，而且是最省事的那个版本。

2.2 复制延迟的三个经典异常

单主复制里没有写冲突，但有另一类问题：从库总是落后主库一点。这个"一点"在正常时候是几毫秒，在主库压力大或网络抖动时可以变成几十秒。三种异常都由它引起，而且各有一个对应的修复手段。

① 读不到自己的写
read-your-writes
用户改完昵称立刻刷新，看到的还是旧昵称——因为写走了主库，读走了从库，而复制还没到。
修复：用户自己修改过的数据，一段时间内的读走主库；或按会话粘性把该用户的读固定到某个足够新的从库；或客户端记住自己最后一次写的位点，只读位点不低于它的副本。
② 时光倒流
monotonic reads
用户刷新两次，第一次看到了新评论，第二次评论消失了——因为两次读随机落到了两个复制进度不同的从库。
修复：让同一个用户的读始终落到同一个副本（按 user_id 哈希路由，而不是随机负载均衡）。
③ 因果错乱
consistent prefix reads
观察者先看到回答"大约十秒"，再看到问题"你能看到多远的未来"——因为问答分别落在两个分区上，各自的复制进度不同。
修复：有因果关系的写入放进同一个分区；或在应用层显式追踪因果依赖（Part 1 的向量时钟就是干这个的）。
这三个不是"最终一致性"的例外，而正是它的定义

最终一致性承诺的只有一件事：如果你停止写入，副本最终会收敛。在收敛之前，上面三种现象全都是被允许的。
所以"我们用了最终一致性"这句话本身几乎没有信息量——真正要问的是：在收敛之前，你给了用户什么保证？上面三条叫会话保证（session guarantees），它们是介于"什么都不保证"和"线性一致"之间的那些实用中间档。

2.3 一致性谱系：把一个词拆成一把梯子

"一致性"是分布式领域最被滥用的词。它至少指三件不同的事：

  • ACID 的 C：应用定义的约束不被破坏（余额非负、外键有效）。本质上由应用代码保证，数据库只提供 A 和 I 来帮忙。和分布式一致性没有关系。
  • 共识里的 agreement：所有节点对同一个值达成一致。Part 3 的主题。
  • 本节说的一致性模型：多个副本对外表现得多像"只有一份数据"。这是一把有层次的梯子。
线性一致
linearizable
系统表现得就像只有一份数据，每个操作在其调用与返回之间的某个瞬间原子生效，且尊重真实时间：只要写操作已经返回，之后开始的任何读都必须看到它。
代价：每次读写都要走一遍共识或读主库，跨地域时延迟很高。etcd/ZooKeeper 的默认读写、Spanner 的读写事务是这一档。
顺序一致
sequential
存在一个所有人都同意的全序，且每个客户端自己的操作在这个全序里保持程序序。
放宽的是：这个全序不必尊重真实时间。你写完 3 秒后我去读，我读到旧值也不违反——只要能找到一个自洽的全序解释。
这就是它和线性一致的唯一区别，也是最容易被忽略的一条。
因果一致
causal
只保证有因果关系的操作所有人看到的顺序一致；并发操作的顺序，不同客户端可以看到不同的样子。
这是实践中的甜点：比最终一致强得多，又不需要全局共识，可用性高得多。Part 1 的向量时钟正是实现它的工具。
最终一致
eventual
只保证停止写入后副本最终收敛。收敛之前任意乱序、任意陈旧，§2.2 的三个异常全部允许。
"最终"没有时限。这是一个弱到几乎没说什么的保证——但也因此可用性最高、延迟最低。

这四级是严格包含关系：线性一致 ⟹ 顺序一致 ⟹ 因果一致 ⟹ 最终一致。越往下保证越弱，可用性和性能越好。选型的本质就是在这把梯子上选一格。

2.4 CAP 的正确读法

CAP 大概是分布式领域被误读最多的一个定理。先把常见的错误说法列出来：

三个流行的错误

✗ "三选二" —— P 不是可选项。只要你的系统跨网络，分区就一定会发生（网线、交换机、机房专线、云厂商的网络抖动）。你不能"选择不要分区容错"，你只能选择分区发生时怎么办。所以真正的选择只有两个：CP 还是 AP。
✗ "MongoDB 是 CP，Cassandra 是 AP" —— 这是系统配置的属性，不是系统的属性。Cassandra 把 W 和 R 都设成 QUORUM 就偏 CP，MongoDB 用 w:1 就偏 AP。
✗ "选了 AP 就没有一致性" —— C 在 CAP 里特指线性一致性。放弃它不等于什么都不保证，因果一致和各种会话保证仍然拿得到，而且它们在分区期间依然可用。

精确的表述是：当网络分区发生时，你必须在"继续响应但可能返回陈旧/冲突数据"和"拒绝服务直到分区恢复"之间二选一。

选择分区期间的行为典型系统与场景
CP少数派侧停止服务（拒绝读写），保证不出错。分区恢复后自动继续。etcd、ZooKeeper、Spanner、配置中心、分布式锁、账务核心。宁可停下，不可出错。
AP两侧都继续服务，各自接受读写，分区恢复后合并（并可能产生冲突）。Cassandra、Dynamo、DNS、购物车、点赞数、CDN 配置。宁可暂时不一致，不可不能用。

更有用的框架：PACELC

if (P) then (A or C) else (L or C)
分区时在可用性和一致性之间选；而在没有分区的正常时候（Else），你仍然要在延迟（Latency）和一致性之间选。

第二半才是你 99.9% 的时间里真正面对的权衡，而 CAP 完全没提。想要线性一致的读，就得走主库或走一遍共识——跨可用区就是几毫秒，跨地域就是上百毫秒。想要低延迟，就得读本地副本，那就得接受陈旧。

这才是日常架构决策的形状。"我们选 CP 还是 AP" 一年可能讨论一次；"这个查询能不能读从库" 你每周都在决定，而那正是 PACELC 的 ELC 部分。

落到一个具体系统上

"计数结果能不能读从库"就是一个纯粹的 ELC 决策。如果写入服务写完之后紧接着有下游服务要读这个结果，那就是读己之写问题——要么这次读走主库，要么下游拿着写入位点等从库追上。
如果只是报表类查询，读从库、容忍几百毫秒陈旧，是完全正确的选择。关键是这个决定要显式做出来，而不是"默认读从库"然后某天被一个偶发的空结果咬到。

2.5 Quorum：本质是交集，不是多数决

Part 0 里我们说过"过半"能防脑裂。现在给出一般形式。设总副本数 N，写入需要 W 个副本确认，读取需要从 R 个副本收集结果：

W + R > N

当这个不等式成立时，任何读集合与任何写集合必然至少有一个共同的副本，于是读一定能看到最新的写。整个 Quorum 机制就建立在这一条上。

"过半"（W = R = ⌊N/2⌋+1）只是这个不等式的一个特解，而且是让读和写都最均衡的那个解。其他解各有用途：

配置特点适用
W=N, R=1写慢读快读远多于写；但任何一个副本挂掉就无法写入，可用性差。
W=1, R=N写快读慢写入吞吐优先；读要等最慢的副本。
W=R=⌊N/2⌋+1均衡默认选择。N=3 时 W=R=2，容忍 1 台故障。
W+R ≤ N不保证读到最新故意的：延迟最低、可用性最高，换来最终一致。Cassandra 的 ONE/ONE 就是这样。

两个必须知道的补充概念

  • 读修复 read repair：读取时如果发现某些副本返回了旧值，顺手把新值写回去。这是最终收敛的主要机制之一。
  • 宽松 Quorum / 提示移交 sloppy quorum & hinted handoff：分区期间，如果目标副本不可达，就把写临时交给别的节点暂存，等目标恢复再转交。这提高了写可用性，但破坏了 W+R>N 的保证——因为写入的 W 个节点可能根本不是"该存这个 key 的那 N 个节点"。这是 Dynamo 系统里一个常被忽略的细节：开了 sloppy quorum，你的"强一致"配置就不再强一致了。

2.6 冲突解决：从丢数据到不丢数据

只要允许并发写（多主、无主，或者单主但多个应用实例竞争同一行），冲突就必然出现。三条路：

① LWW
last-write-wins
按时间戳或到达顺序二选一。简单，但一定丢掉一条写入（Lab 1-3 已经量化过：丢弃率恒为 100%，时钟准不准只改变"丢哪一条"）。
可用场景：心跳时间、在线状态这类"幂等且可丢"的数据。
② 保留 siblings
交给应用合并
用向量时钟检测出并发，两条都留着，下次读的时候把冲突版本一起返回给应用。不丢数据，但把复杂度推给了业务代码，而且要处理"用户看到两个版本"的产品问题。
Riak、Dynamo 购物车（合并策略：取并集）。
③ CRDT
无冲突复制数据类型
把数据类型设计成合并操作满足交换律、结合律、幂等律，于是无论以什么顺序、重复多少次合并，结果都相同——冲突在数学上就不可能存在。
代价：不是所有语义都能表达成 CRDT。

四个最常用的 CRDT

类型结构与合并用途
G-Counter
只增计数器		每个副本维护一个向量 [c1..cN]，只增自己那位。
合并 = 逐位取最大；取值 = 求和。		浏览量、点赞数。和 Part 1 的向量时钟是同一个结构。
PN-Counter
可增可减		两个 G-Counter：一个记增、一个记减。取值 = 增和 − 减和。库存、赞/踩。
G-Set / OR-Set
集合		G-Set 只能加，合并 = 并集。OR-Set 给每个元素带唯一 tag，支持删除且"加"优先。购物车、标签、好友列表。
LWW-Register值 + 时间戳，合并取时间戳大的。注意：它是 CRDT，但仍然丢数据——CRDT 保证的是"所有副本收敛到同一个值"，不保证"不丢写入"。这两件事是分开的。
这类 SQL 和 CRDT 的关系

ON CONFLICT DO UPDATE SET cnt = t.cnt + EXCLUDED.cnt
这个合并操作满足交换律和结合律（加法），所以并发写不会丢——但它不满足幂等律，同一条消息重复投递会多加一次。所以它是"可交换的"而不是完整的 CRDT，用它的前提是投递侧必须去重（Lab 0 的幂等键）。
真正幂等的做法是 G-Counter 那种：SET cnt_by_source = jsonb_set(..., GREATEST(old, new)) —— 逐位取最大，重复合并结果不变。

2.7 回到一个具体表：一份判断清单

把这一章用到 counters 上。按顺序问自己四个问题：

1
真的是单写者吗？
"只由一个写入服务写"如果指的是单个进程，那你没有并发写，本章后半段的问题都不存在，可以直接跳到问题 4。
如果这个服务在 K8s 上跑多副本，那两个 pod 会并发写同一行——它是多写者，只是写者名称相同。此时要么按 key 分片路由（同一个 key 永远落到同一个 pod），要么老老实实处理冲突。
2
并发写的语义是"覆盖"还是"合并"？
覆盖（这次计算的结果替代上次）→ DO UPDATE SET ... = EXCLUDED.... 是对的，lost update 在语义上无害。
合并（多个来源各自贡献一部分）→ 整行覆盖一定会丢，要改成字段级合并或加版本号条件写。
3
需不需要知道"这次写是基于哪个版本算出来的"？
如果写入服务采用"读旧值 → 计算 → 写新值"这种读改写模式，整行覆盖会丢掉中间那次更新（经典 lost update）。修复：加一个 version 列，写的时候带 WHERE version = :read_version，冲突了就重读重算。这就是乐观锁。
4
下游读这张表，能不能读从库？
这是 PACELC 的 ELC 部分。写入服务写完立刻有下游要读 → 读己之写问题，这次读走主库。只是报表 → 读从库没问题。显式决定，不要默认。
顺便再提一次 Part 1 说的那个坑

如果 raw_events → counters 这条链路是用 updated_at 做增量游标的，去查一下长事务导致的漏拉问题——那个 bug 和时钟准不准无关，纯粹是"打戳时刻 ≠ 可见时刻"，而且它不留任何痕迹。

2.8 自测题

先自己想 30 秒再展开。

1. 线性一致和顺序一致，唯一的区别是什么？

是否尊重真实时间。

两者都要求存在一个全序，且每个客户端自己的操作在全序里保持程序序。线性一致额外要求：如果操作 A 在操作 B 开始之前就已经返回，那么 A 在全序里必须排在 B 前面。

实际后果：你写完并收到成功响应，3 秒后我去读，顺序一致允许我读到旧值（只要能找到一个自洽的全序把我的读排在你的写之前）；线性一致禁止。这就是为什么线性一致必须走主库或走共识——它需要一个真实时间上的同步点。

2. 为什么说 CAP 的"三选二"是错的？

因为 P 不是可选项。只要系统跨网络，分区就一定会发生——你不能选择"不要分区容错"，你只能选择分区发生时的行为。

所以真正的选择只有二选一：分区期间是继续服务（AP，可能返回陈旧或冲突数据），还是拒绝服务（CP，少数派停摆）。而且这是系统配置的属性而非系统本身的属性：Cassandra 把 W/R 设成 QUORUM 就偏 CP，MongoDB 用 w:1 就偏 AP。

3. PACELC 比 CAP 多说了什么？为什么那部分更重要？

多说了 ELC：没有分区的正常时候，你仍然要在延迟（Latency）和一致性（Consistency）之间权衡。

这部分更重要，因为分区是罕见事件，而延迟-一致性的权衡是你每天都在做的决定："这个查询能不能读从库？"就是一次 ELC 决策。想要线性一致的读就得走主库或共识（跨可用区几毫秒、跨地域上百毫秒），想要低延迟就得读本地副本并接受陈旧。CAP 对这个 99.9% 的时间只字未提。

4. Quorum 的 W+R>N 保证了什么？它的本质是什么？

保证任意读集合与任意写集合必然有交集，于是读一定能碰到至少一个持有最新值的副本。

本质是集合的交集性质，不是"少数服从多数"。"过半"只是 W=R=⌊N/2⌋+1 这一个特解，它恰好让读写负载最均衡。理解这一点后，W=N,R=1（写慢读快）和 W=1,R=N（写快读慢）就都是同一个不等式的另外两个解，各有适用场景。

5. 开启 sloppy quorum 之后，W+R>N 还成立吗？

不成立了。sloppy quorum 在目标副本不可达时，把写临时交给其他节点暂存（hinted handoff），等目标恢复再转交。

于是"写入的那 W 个节点"可能根本不在"该存这个 key 的那 N 个节点"里，读取时从 R 个正规副本里读，可能一个都碰不到那次写。它用一致性换写可用性。这是 Dynamo 系风格系统里最常被忽略的一个配置项：开了它，你自以为的"强一致"配置就不再强一致了。

6. §2.2 的三个复制延迟异常，各自的修复手段是什么？共同点是什么？
  • 读不到自己的写 → 用户自己改过的数据读主库；或客户端带上自己最后一次写的位点，只读追上该位点的副本。
  • 时光倒流 → 同一个用户的读固定路由到同一个副本（按 user_id 哈希，而非随机负载均衡）。
  • 因果错乱 → 有因果关系的写放进同一个分区；或显式追踪因果依赖（向量时钟）。

共同点：三个修复手段没有一个是"把复制延迟调小"。调小延迟只是降低了发生概率，把偶发故障变成更难复现的偶发故障。真正的修复都是改变路由或依赖追踪——也就是给系统加上一个明确的保证，而不是指望运气。

7. CRDT 保证"收敛"，这等于"不丢数据"吗？

不等于。CRDT 保证的是：无论以什么顺序、重复多少次合并，所有副本最终得到同一个值。它不保证那个值是"正确"的。

最好的反例就是 LWW-Register：它是一个合法的 CRDT（合并=取时间戳大的，满足交换律结合律幂等律），所有副本必然收敛，但它照样丢掉一条并发写。收敛是关于"最终一致"的性质，不丢数据是关于"语义"的性质，两者正交。G-Counter 之所以两样都有，是因为它的合并操作（逐位取最大）恰好也保留了全部信息。

8. ON CONFLICT DO UPDATE SET cnt = t.cnt + EXCLUDED.cnt 是一个完整的 CRDT 吗？

不是，它少了幂等律。加法满足交换律和结合律，所以并发写不会丢；但同一条消息重复投递会多加一次。

所以用它的前提是投递侧必须去重——回到 Lab 0 的幂等键。真正幂等的做法是 G-Counter 那种按来源分槽、合并时逐位取最大：重复合并同一份数据结果不变。这也是为什么 Kafka 的 exactly-once 和 CRDT 是互补而非替代关系。

9. 一个服务在 K8s 上跑 3 个副本，都写同一张表的同一行。这算单主复制吗？会有什么问题？

数据库层面是单主（只有一个 PostgreSQL 主库），但应用层面是多写者。三个 pod 会并发提交更新到同一行。

数据库的行锁会把它们串行化，所以不会有"数据分叉"，但会有 lost update：如果每个 pod 是"读旧值 → 计算 → 写新值"，那么 pod A 读到 v1、pod B 也读到 v1，两者各自算完写回，后写的覆盖先写的，A 的计算结果消失。

三种修复：① 按 key 分片路由，同一行永远只由一个 pod 处理（把多写者变回单写者，最省事）；② 乐观锁——加 version 列，写时 WHERE version = :read_version，冲突就重读重算；③ 把操作改成可交换的形式（SET c = t.c + delta），根本不需要先读。

10. 【综合】设计一个"文章点赞数"功能，多机房部署。逐条走一遍这一章的决策。

① 复制拓扑：点赞是高频写、跨地域，单主会让远端机房写入延迟很高。倾向多主或无主。

② 一致性档位：点赞数不需要线性一致。用户看到的数字差几个不影响任何决策。选最终一致，配上读己之写（我点了赞，我自己刷新必须看到自己那一票，否则会重复点）。这就是典型的"整体弱、局部强"。

③ 冲突解决：点赞语义是累加，LWW 一定丢——两个机房同时 +1，整数覆盖后只剩 +1。用 PN-Counter（可增可减，支持取消赞），按机房分槽，合并逐位取最大。

④ 落到实现：每个机房维护 likes_by_dc: {dc1: 1042, dc2: 887, dc3: 15}，本机房只增自己那一槽；展示时求和；跨机房同步用逐位取最大，天然幂等，重传无害。

⑤ 读己之写：用户点赞后，本地立刻乐观更新 UI，并把"我赞过"这个事实存在本机房（用户天然绑定机房）。这样即使跨机房同步慢几秒也不影响体验。

⑥ 去重：同一用户重复点赞用唯一约束拦（(user_id, article_id) 唯一索引 + ON CONFLICT DO NOTHING）——Lab 0 的幂等键。注意这一层用的是 first-write-wins，和计数层的 CRDT 是两个不同的机制，各管一段。

如果你能自己想到 ③ 和 ⑥ 是两个独立机制，说明这两章已经串起来了。
